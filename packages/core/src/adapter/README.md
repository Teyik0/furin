## Adapter contract

A deployment target is a `FurinAdapter` (`types.ts`):

- `name` — build directory, analysis file prefix and manifest key;
- `capabilities` — `{ assets, publicCache, websocket }`, baked into each
  compile context; the production runtime reads them instead of a platform
  name;
- `runtimeModule` — a typed module bundled as the server entry. It imports the
  application from `furin:app` (the generated, listener-free `_furin-app.ts`);
- `onBuildComplete(output)` — receives data only (apps, routes, prerendered
  paths, the server bundle files) and writes the platform layout.

`build.ts` owns everything shared: per-app client builds (in parallel, no
process-global state), the RSC graph, the application entry, the one ordered
server plugin chain (`server-bundle.ts`), and the prerender pass. Prerendering
runs **inside the built bundle**, in a child process (`prerender.ts`): it lists
the known SSG/ISR URLs and, when `publicCache` is `"framework"`, renders the SSG
snapshot into the `furin-prerender.json` sidecar the bundle imports at runtime.

## Bun adapter

Three outputs from one JavaScript bundle (`server.js` + `_furin-app.js` +
chunks):

- the bundle itself, beside `client/` and `public/`;
- `--compile server`: an executable built from the bundle, assets on disk;
- `--compile embed`: an executable with client/public directories
  [embedded](https://bun.com/docs/bundler/executables.md).

Compiling re-bundles the finished JavaScript, so the executable carries the
snapshot the bundle rendered. Elysia AOT evaluates the listener-free
application entry; `adapter/bun/server.ts` owns the listener.

Mount discovery and AOT compilation expose Elysia's `inAotBuild()` guard to
application modules. Sync adapter factories are skipped in those phases and
prepared once during real application composition, before listening. The
application must guard its own service acquisition and keep route declarations
independent of runtime resources. Prerendering is separate: SSG/ISR loaders
execute normally and still need their resources.

## Vercel adapter

The Vercel target emits Build Output API v3 directly to `.vercel/output`:

- content-hashed browser assets and `public/` files under `static/`;
- one bundled `bun1.4.x` Web Handler under `functions/__server.func`;
- SSG Prerender Functions with no timed expiration and build-time fallbacks
  for known URLs whose route tree has no query-dependent input;
- ISR Prerender Functions using each route's `revalidate` duration and
  build-time fallbacks for fixed URLs or `staticParams()` values when the route
  tree has no query-dependent input;
- a filesystem-first route table with a server fallback for SSR and APIs;
  navigation data requests (`?_furin=data`) always reach the server.

The typed handler (`adapter/vercel/handler.ts`) reads its route data from
`furin-vercel.json`, connects Furin cache invalidation to Vercel cache tags
and keeps background ISR work alive with `waitUntil`.

The Function bundle uses the same Elysia AOT capture path with the Bun target.
No custom Elysia runtime adapter is needed: Vercel invokes the application's
Web-standard `handle(Request)` API inside its Bun runtime.
For Furin Sync, the Vercel target streams browser cursor notifications through
Server-Sent Events at `/_furin/events`. Bun servers keep the WebSocket transport.
Both transports use the durable sync recovery endpoint after reconnects (`/_furin/sync/changes` by default, configurable with `sync.path`).

Vercel Prerender Function invocations bypass Furin's process-local SSG/ISR
cache. The CDN owns freshness and each regeneration returns newly rendered
HTML; the in-memory cache remains exclusive to development and Bun targets.

The handler also installs Vercel Runtime Cache as the provider behind
`@teyik0/furin/cache`. Application code keeps one portable cache API while
development and Bun targets fall back to the in-memory provider.

Application `@elysia/static` mounts are rejected during Vercel builds: their
runtime filesystem mappings are not deployable CDN mappings. Place static files
under `public/` instead. PPR pages produce a cached public HTML shell, postponed
React state and public loader snapshot atomically. Vercel's native `chain`
continuation runs private request loaders and resumes React without caching the
personalized output. Build-time shells are generated by the production bundle
itself, ensuring the minified component tree remains compatible with its state.

Successful navigation data responses (`?_furin=data`) for SSG/ISR routes share the document's
cache tag and revalidation window. SSR, request-loader, deferred, and failed
navigation responses remain `private, no-store`.

JSON-only navigation data uses a compact JSON envelope. CrossJSON and Route
Frames remain the lossless transports for rich values, shared references,
deferred data, and RSC payloads.

The Vercel Function starts through a lightweight `index.js` bootstrap
(`adapter/vercel/bootstrap.ts`). Its
first request logs a `vercel_cold_start` event and every dynamic response
exposes `furin_module_init`, `furin_server_init`, `furin_handler_wait`, and
`furin_handler` through `Server-Timing`. `--analyze` writes both Vercel client
and server metafiles under `.furin/build/analysis`.
