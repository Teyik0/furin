# Integrate Furin and Elysia

Desktop packaging keeps the original Elysia root, route types, decorators, prefixes and Eden inference. Your Furin routes, APIs and sync runtime remain the application; `desktopApp()` adds window, session and lifecycle ownership around them.

## One listener

`.listen(...)` is the source of truth for the backend: Web and desktop clients share its hostname, scheme and port, and windows never configure a second server address.

Builds capture the listener options without opening a socket or running startup hooks; the generated host then starts the built application with them. Shared initialization belongs in `.onStart()`, not in native module top-level code.

If an entry only default-exports its application without a listener address, the desktop host uses `127.0.0.1` and a free port. Managed windows reach wildcard listeners through loopback (`0.0.0.0` becomes `127.0.0.1`, `::` becomes `[::1]`); explicit hostnames and HTTPS are preserved. Unix sockets are rejected because the WebView needs an HTTP(S) address.

## Use existing services

`desktopApp()` accepts static options, or a factory that receives the decorators registered before it plus `store`. A factory can read existing services:

```ts
import { desktopApp } from "@teyik0/furin-electrobun/server";
import { Elysia } from "elysia";

new Elysia()
  .decorate("appName", "Relay")
  .state("background", false)
  .use(desktopApp(({ appName, store }) => ({
    window: { title: appName },
    background: () => store.background,
  })));
```

The factory runs synchronously once, when the plugin is installed. Register its services first; it does not wait for `.onStart()` or pending async plugins. The context holds decorators and `store` only, not request fields or per-request `.derive()` values.

Plain values such as the title are read at installation; callbacks such as `background` and `admission` read their dependencies each time they run. The explicit form `.use((app) => desktopApp(app, configure))` provides the same context.

## Independent API plugins

Each independent API plugin explicitly installs `desktopContext` for its own inferred context:

```ts
import { desktopContext } from "@teyik0/furin-electrobun/server";
import { Elysia, status } from "elysia";

export const desktopApi = new Elysia({ prefix: "/api/desktop" })
  .use(desktopContext)
  .post("/minimize", async ({ desktop }) => {
    if (!desktop) return status(409, { error: "Desktop unavailable" });
    await desktop.window.minimize();
    return { ok: true };
  });
```

`desktopContext` is named and deduplicated. It injects the desktop controller (`null` in Web mode, without loading native SDK code) and registers no root, listener or window. The root `desktopApp()` plugin installs it automatically; independent plugins `.use()` it to get their own types.

Every controller call is asynchronous, with plain-data (JSON) arguments and results. A packaged app runs it in the same process; in development it crosses the channel to the native shell, so code behaves the same once packaged. The controller exposes:

| Member | Purpose |
|---|---|
| `desktop.window` | The main window's serializable SDK `BrowserWindow` methods (`minimize`, `setTitle`, `getFrame`…); calls reject while it is closed |
| `desktop.open()` | Reactivate or recreate the main window |
| `desktop.windows.create(name, options)` | Open an authenticated managed window at `options.path` and resolve to its handle; options exclude `rpc`; `"main"` is reserved |
| `desktop.windows.get(name)` | Handle for a managed window; calls reject while it is not open |
| `desktop.native` | Commands exported by the [native entrypoint](/docs/desktop/native-apis#call-native-code-from-elysia), typed from it |
| `desktop.quit()` / `desktop.restart()` | Coordinated shutdown with window fencing and one-time backend cleanup |
| `desktop.updates.install()` | Install a downloaded update after draining the backend |
| `desktop.browser.open(path?)` | Open an application path (default `/`) in the system browser with a fresh one-use session. Returns `false` when the browser cannot be opened, always on TLS listeners |
| `desktop.associations.read(target)` / `requestDefault(target)` | Read or request file-association and URL-scheme defaults |
| `desktop.snapshot()` | `{ background, phase, trayVisible, webviews, windows }` |

> [!CAUTION]
> `desktop.open()` rejects before native readiness, and in development while the native shell is not connected: do not await it during startup.

## Authentication and storage

Managed desktop windows are authenticated: over HTTP through one-use bootstrap URLs, over TLS through a verified native session cookie installed before navigation. A regular browser does not share a window's session. To accept network clients, authenticate them with the `admission` option of `desktopApp()` rather than removing the desktop session boundary.

The host resolves the data directory (`desktop.dataDir`, or a per-identifier app-data folder by default) and sets `FURIN_APP_DATA_DIR` before importing the application. Build persistent paths from it instead of the working directory, with a fallback for Web-only runs where it is unset.
