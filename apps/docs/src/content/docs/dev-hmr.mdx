# Development HMR Internals

Furin development mode is one Bun process, but it is not one module graph.
Bun owns the browser bundle and HMR transport. Furin owns the extra work needed
to keep server rendering, route data, route topology, and diagnostics consistent
with that browser graph.

This page documents the internal contract. Application code does not call any
of the functions or endpoints described here.

## Architecture at a glance

Four loops run together during development:

```text
source edit
  ├─ Bun browser graph ──────> hot module ──────> React reconciliation
  ├─ Furin SSR graph ────────> versioned import -> next SSR/data request
  ├─ route/data coherence ───> rescan + invalidate -> fresh loader result
  └─ diagnostics ────────────> error/ready event -> development overlay
```

They meet at two generated files in `.furin/`:

- `_hydrate.tsx` contains the client route table, hydration entry, stable hot
  component registry, loader refresh hook, and HMR connection recovery.
- `index.html` is Bun's HTML entry. Furin mounts its `HTMLBundle` at
  `/_bun_hmr_entry`, under the instance prefix when one exists.

Bun scans the HTML entry, bundles its scripts and styles, and supplies the
browser WebSocket and `import.meta.hot` runtime. Furin does not implement a
second HMR transport.

## Architecture decision

Furin deliberately keeps a hybrid boundary: use Bun for browser invalidation and
implement framework-specific coherence inside Furin.

| Option | Benefit | Cost | Decision |
| --- | --- | --- | --- |
| Bun HMR plus Furin coherence | One process and one browser bundler; preserves React state while keeping SSR and loaders fresh | Furin must maintain versioned server imports, route rescanning, and diagnostics | **Selected** |
| Full-page reload after every edit | Smallest implementation | Loses local state and hides invalidation bugs | Rejected |
| Vite or Rsbuild development server | Mature HMR graph, plugin lifecycle, and error handling | Introduces a second development architecture and weakens the Bun-only design | Rejected |
| Bun HMR alone | No framework orchestration | Browser code can move ahead of SSR modules, loaders, and the route snapshot | Insufficient |

The recommended direction is to keep the Bun-native boundary and harden it with
observable conformance tests. Next.js owns a deeper integrated compiler graph,
while TanStack Start delegates development HMR to Vite or Rsbuild. Copying either
approach would trade away Furin's defining single-process constraint rather than
improve it incrementally.

## Startup

Running the application with `bun --hot` initializes development mode in this
order:

1. Register the `furin-dev-page-loader` runtime plugin.
2. Scan `pagesDir` and build the initial root, route, and Elysia snapshots.
3. Generate `.furin/_hydrate.tsx`, `.furin/index.html`, and route types. Files are
   rewritten only when their content changed, so generated output does not cause
   a reload loop.
4. Import the generated HTML as a Bun `HTMLBundle` and mount it at the instance's
   `/_bun_hmr_entry` path.
5. Start a per-instance route watcher. It polls authored route files and their
   dependencies every 100 ms, serializing refreshes so requests cannot observe a
   partially replaced route snapshot.
6. Mount the data, diagnostics, DevTools, sync, public asset, and not-found
   handlers around the generated Elysia route tree.

Route modules are not eagerly imported into the ordinary server watcher graph.
They are loaded through a virtual namespace on demand, so editing a page can use
browser HMR without restarting the whole server module graph.

## Server rendering stays fresh

### One identity per source revision

Every dev request resolves `root.tsx` and the matched page through a versioned
specifier:

```text
/absolute/path/to/page.tsx?furin-server&t=<source-version>
```

`<source-version>` is derived from the file's nanosecond modification time,
size, and an explicit generation counter. It is not `Date.now()` and it does not
change for every request.

Furin caches the import promise by source path and version. Concurrent requests
for the same revision share one evaluation; a new edit gets a new module
identity. This avoids both stale SSR code and unbounded, request-proportional ESM
registry growth.

Relative imports inside a versioned module are resolved to absolute paths. Local
JavaScript and TypeScript dependencies receive their own source version, so an
edited helper cannot remain stale behind a fresh page module. Failed imports are
removed from the cache and can recover on the next edit.

### Virtual server transform

The `furin-dev-page` namespace has no filesystem directory from which Bun can
resolve relative imports. Its loader therefore performs the complete transform
before returning JavaScript:

1. Record application imports in the development module graph.
2. Select the server side of isomorphic functions.
3. Rewrite relative imports to absolute, versioned specifiers.
4. Transpile TypeScript and JSX with `Bun.Transpiler`.
5. Resolve bare imports from the authored module's directory.
6. Canonicalize React and React DOM imports.
7. Inject the JSX runtime helpers emitted by the transpiler.

Transform failures retain a distinct `transform` diagnostic phase instead of
being reported as generic import failures.

### Root and nested layouts

A fresh page import does not guarantee that a statically imported parent layout
has a fresh identity. Before rendering, `refreshLayoutChain()` imports each
existing intermediate `_route` module with the same versioning rule and patches
the matching runtime chain entry.

Directories without `_route` files do not consume a chain position. The root is
loaded separately, then its current layout and loader references replace the
root entry captured by the nested chain.

Furin finally rebuilds the `ResolvedRoute` from the current page and route chain.
Changing `mode`, adding or removing a loader, changing `revalidate`, or changing
cache tags therefore takes effect without a manual restart. Structural fields
such as the URL pattern and convention boundaries come from the topology
snapshot and change through the watcher instead.

### Render and document assets

After the route is rebuilt, Furin runs the applicable loaders and renders the
current React tree. The SSR document receives the latest loader payload and the
assets parsed from `/_bun_hmr_entry`.

The development HTML template and parsed asset metadata use a one-second cache.
This bounds internal fetch and parsing work while allowing Bun's content-addressed
entry and stylesheet URLs to converge quickly after a rebuild. Furin tracks the
main client entry separately from framework modules such as the error overlay,
so a React-rendered `<Scripts />` element restores both classes of scripts.

## A live browser update

Route modules receive a client transform before Bun bundles them. The transform:

- removes server-only builder stages such as `loader`, `requestLoader`, `head`,
  `params`, `query`, and `staticParams`;
- records the route component's hook-call signature;
- wraps imported route components so they participate in React refresh; and
- installs a self-accepting `import.meta.hot.accept()` callback.

When Bun delivers an updated route module, the callback forwards the new
component to `window.__FURIN_HMR_UPDATE__`.

### Stable component identities

The generated hydrate entry keeps a registry on
`window.__FURIN_HOT_COMPONENTS__`. Each page, layout, and root has a stable
wrapper keyed by role and source path. An edit replaces the implementation
behind that wrapper rather than replacing the wrapper itself.

If the hook signature is unchanged, React can preserve compatible local state.
If the signature changes, Furin replaces the inner boundary and React remounts
that component. Rebuilding the route table removes obsolete registry entries
without replacing surviving entries.

### Reconcile, then refresh data

The initial document calls `hydrateRoot(document, app)`. The React root is kept
on `window.__FURIN_ROOT__`, the object that survives Bun module re-evaluation.
Subsequent updates call `root.render(app)`; they reconcile an already-owned DOM
and never attempt to hydrate it a second time.

After the component update, Furin schedules `window.__FURIN_HMR_REFRESH__` on the
next animation frame. The router:

1. invalidates the current page's prefetch entry;
2. requests fresh route data with `x-furin-hmr-refresh: 1`;
3. asks the topology watcher to refresh before resolving that data request;
4. reruns or retrieves loaders according to the current route mode; and
5. replaces the current router state without adding a history entry or resetting
   scroll.

Navigation versions and abort signals prevent an older, slower loader response
from overwriting a newer refresh. Code and data still arrive as two updates, so
a loader-backed component can briefly render its new code with the previous
payload before the data request converges.

### Transport recovery

Ordinary accepted edits do not reload the document. If Bun's native HMR
WebSocket disconnects and later reconnects, Furin performs one page reload to
restore a known-good module graph. This intentionally sacrifices local state
only after a transport outage.

## Route topology changes

The generated Elysia tree is static, but its renderers dispatch through a
replaceable development snapshot. The topology watcher distinguishes two cases:

- An existing route or dependency changed: invalidate server module identities,
  reload the route snapshot, and regenerate client files if their content
  changed.
- A route or convention appeared or disappeared: rescan the filesystem, replace
  the matcher and renderer snapshot, and regenerate the client route table.

This makes hot addition and removal work for pages, `error` files, and
`not-found` files. A newly added path reaches the refreshed renderer through the
Elysia not-found fallback; a removed active page resolves to the current
not-found boundary.

Route config auto-fix runs before each snapshot refresh. Because generated files
are content-diffed and watcher signatures are resynchronized after a rewrite,
the fix cannot create its own update loop.

## Loader and render-mode coherence

Development SSR treats each render mode deliberately:

| Mode | Loader behavior | HTML behavior |
| --- | --- | --- |
| SSR | Run the current loader chain for every request | Render from current source |
| SSG | Cache synchronous loader data until a tracked source changes | Re-render HTML for every request |
| ISR | Cache synchronous loader data for `revalidate`, unless a tracked source changes first | Re-render HTML for every request |

Only loader output is cached in development. HTML is always assembled again so
the response can carry current code, document assets, and framework scripts.
Deferred promises are not reused from an SSG or ISR cache hit.

Each cache entry records the page, root, and existing intermediate layouts that
can affect it. A source re-evaluation invalidates only entries indexed by that
file. The validity check also compares dependency modification times, so a
rename or deletion fails conservatively instead of serving stale data.

Changing the route mode is safe because the mode is recomputed from the freshly
adapted route before selecting the SSR, SSG, or ISR path.

## Development diagnostics and recovery

Furin has a framework-level diagnostic pipeline in addition to Bun's bundler
errors. It covers failures that occur after a module was delivered or while a
request is executing.

| Phase | Origin |
| --- | --- |
| `transform` | Furin's server transform or parser |
| `import` | Route evaluation or a transitive application import |
| `loader` | Root, layout, or page loader execution |
| `render` | Server React render |
| `hydrate` | Initial browser hydration |
| `client-render` | React render after the browser owns the document |

Server failures become a structured diagnostic and a `500` document containing
the overlay bootstrap. Client hydration and render failures dispatch a
`furin:client-error` event; the overlay posts the report back to the server for
source-map symbolication.

The diagnostic contains the phase, route, message, cause, source location,
application import chain, and stack. The import chain comes from the module graph
recorded during transforms. Client frames are mapped through same-origin Bun
source maps, and framework or dependency frames are classified as internal.

The browser receives a small versioned diagnostic channel over Furin's shared
`/_furin/events` WebSocket:

- `furin.error` shows or replaces the active overlay;
- `furin.ready` clears a warm overlay after a successful route revision;
- a cold `500` page reloads automatically after recovery; and
- a changed server id also reloads, because event cursors from the previous
  process no longer describe the current graph.

The store retains the latest active error and a bounded event history, allowing
a newly opened tab or a reconnecting socket to recover its state. Sync,
diagnostics, and DevTools share this one connection instead of occupying three
long-lived HTTP response slots per tab.

The internal endpoints live under the instance prefix:

```text
/_furin/dev/overlay.js
/_furin/dev/client-errors
/_furin/events
/_furin/events/client.js
```

They accept loopback and same-origin development requests only. Production keeps
the diagnostic plugin out of the server graph and resolves the remaining
development boundaries to inert implementations before bundling.

## Module identity invariants

### React is a server singleton

Every SSR module must observe the same React dispatcher used by
`react-dom/server`. A second React identity causes `Invalid hook call` or a null
hook dispatcher after hot reload.

Furin canonicalizes these imports to resolved on-disk paths:

- `react`
- `react/jsx-runtime`
- `react/jsx-dev-runtime`
- `react-dom`
- `react-dom/server`
- `react-dom/client`

Workspace modules that remain in Bun's normal server graph receive the same
singleton rewrite, not only virtual page modules.

### The client router is a singleton

The generated hydrate entry and application code must import `RouterProvider`
and `Link` through the same package identity. Otherwise two `RouterContext`
objects can exist: the provider writes one while links read the other and fall
back to document navigation.

The hydrate entry therefore imports router APIs through
`@teyik0/furin/link`, never through an absolute internal source path.

## Multi-instance isolation

Every mounted Furin instance has its own prefix, generated `.furin` directory,
route snapshot, route watcher, template cache, loader caches, diagnostics store,
and internal endpoints. A hot update or invalidation in one prefixed application
must not affect a sibling instance.

The root instance alone writes the shared `furin-env.d.ts`; prefixed instances
use their own client entry without competing for that file.

## Observable edit behavior

| Edit | Expected result |
| --- | --- |
| Page component | Preserve compatible React state; render the latest implementation |
| Hook order or signature | Remount the affected component; keep unaffected parents mounted |
| Root or nested layout | Patch the stable component and refresh the server route chain |
| Loader, mode, or `revalidate` | Refresh route data using the newly rebuilt route definition |
| Imported local module or re-export | Propagate through the browser graph and use a versioned SSR dependency |
| Route or convention add/remove | Replace route snapshots and regenerate the client table without a manual restart |
| CSS or `@import` dependency | Let Bun update styles while React state remains mounted |
| Server entry, API, or runtime internals | Let `bun --hot` re-evaluate the affected server graph |
| HMR transport reconnect | Reload once to recover a known-good graph |

## Known limitations

The current Bun-backed pipeline has executable `test.todo` specifications for:

- editing a dynamic import before its first execution;
- creating a previously missing import;
- restoring a deleted imported component;
- pruning a stylesheet after its component import is removed; and
- CSS Module class mapping imports in Bun's full-stack development bundle.

Furin does not hide these cases behind a global reload because that would make
the passing Fast Refresh cases lose state and would conceal graph invalidation
regressions.

Loader-backed edits are not atomic: code can render once with the previous data
before the refresh resolves. Large-project cold start, warm start, memory, and
edit-to-paint performance also need published reproducible benchmarks before
making comparative speed claims.

## Verification

The HMR suite treats browser-visible behavior as the public contract.
Run these commands from `packages/core`:

- `bun run test:webview` runs the real-browser conformance tier with
  `Bun.WebView` and Chrome.
- `FURIN_WEBVIEW_TESTS=1 bun test --todo tests/browser/hmr-conformance.webview.test.ts`
  runs the known-gap specifications from `packages/core`.
- `bun run test:hmr:soak` runs the endurance tier with 2,000 edits by default.
  `FURIN_HMR_SOAK_EDITS=<count>` selects a shorter local run.

The suite covers state preservation and remounting, re-exports, cycles, loaded
dynamic imports, layouts, syntax and runtime recovery, the diagnostic overlay,
CSS, rapid edits, stale loader responses, route topology, SSR/SSG/ISR, deferred
data, composite RSC, prefixed instances, multiple tabs, reconnections,
edit-to-paint, and memory behavior.

## Related development tooling

Furin DevTools is mounted automatically in development and reports route,
request, loader, cache, payload, asset, and sync telemetry. It is adjacent to
HMR but not part of the invalidation protocol: diagnostics answer "why did this
revision fail?", while DevTools answers "what did the successful request do?".

DevTools endpoints live under `/_furin/devtools/*`, are scoped by instance, and
are excluded from production together with their instrumentation implementation.
