# Sync & Invalidations

Furin Sync adds three guarantees around Elysia mutation routes:

1. an `Idempotency-Key` identifies retries of the same principal and request;
2. a successful bounded response can be replayed without running the handler again;
3. committed cache invalidations enter an ordered change journal consumed by other browsers.

Use it for repeatable application mutations whose response is small and whose clients benefit from automatic cross-tab refresh. It is not a transaction manager for arbitrary external side effects.

## Configure One Runtime

Bind the ORM once in the adapter configuration, then pass the same `sync` object to the page plugin and the mutation plugin:

```ts
// src/sync.ts
import type { FurinSyncOptions } from "@teyik0/furin/sync";
import { drizzleSyncAdapter } from "@teyik0/furin/sync/drizzle";
import { migrateSqliteSync } from "@teyik0/furin/sync/sqlite";
import { requireUser } from "./auth";
import { db } from "./db";

// db is a Drizzle bun:sqlite database. Run this migration at deployment.
migrateSqliteSync(db.$client);

export const sync = {
  adapter: drizzleSyncAdapter({ db, namespace: "my-app" }),
  principal: ({ request }) => requireUser(request).id,
} satisfies FurinSyncOptions;
```

```ts
// src/server.ts
import { Elysia } from "elysia";
import { furin } from "@teyik0/furin";
import { api } from "./api";
import { sync } from "./sync";

new Elysia()
  .use(await furin({ pagesDir: "./src/pages", sync }))
  .use(api)
  .listen(3000);
```

`satisfies FurinSyncOptions` types the callbacks while keeping the adapter's inferred transaction type; later snippets omit that import.

- `namespace` separates applications sharing the same database.
- `principal` must authenticate the request and return a stable, non-empty identity, for example by verifying a signed session as `requireUser` does above. It scopes idempotency keys, so two users can safely use the same client-generated key, and the same callback authorizes journal recovery. Never return an unverified header or a client-supplied user ID: hashing a principal separates journal entries but does not authenticate a request.
- Passing `sync` to `furin()` mounts the change endpoints and injects the browser event transport.
- The optional `path` property moves the durable endpoints from `/_furin/sync`; with `path: "/_internal/sync"`, catch-up is served at `/_internal/sync/changes`. Browser notifications always use `/_furin/events` under the Furin instance prefix.

`mutation()` validates and normalizes its response with the guards and models of the final application. The application that mounts `furin({ sync })` is bound automatically. Without Furin (standalone Elysia), or when you remount a complete application under another root and call `handle()` on it, install `furinSync(sync)` on that final root as well. A mutation reached through an unbound root is rejected before the business callback runs; Furin never commits using only a child's response schema.

### Principal Secret

Furin sends a hash of the principal to the browser (the `session` of identified reads, used to drop a previous user's cached data) and stores it in the journal's `principal_hash`. Without a secret this is plain SHA-256, so an email or sequential ID can be recovered by hashing guesses. Set `secret` to key it with HMAC-SHA256:

```ts
export const sync = {
  adapter: drizzleSyncAdapter({ db, namespace: "my-app" }),
  principal: ({ request }) => requireUser(request).id,
  secret: process.env.FURIN_SYNC_SECRET, // e.g. `openssl rand -base64 32`
} satisfies FurinSyncOptions;
```

- The secret must be at least 32 characters; shorter values throw at startup. Never prefix the variable with `FURIN_PUBLIC_`.
- Use the same secret on every node. Browsers compare `session` values across responses, and a node with another secret looks like a different user and clears that browser's queries.
- Setting or rotating the secret is safe. Journal entries hashed with the previous value no longer match, so recovery takes the full-refresh path described in [Browser Catch-Up](#browser-catch-up), and browsers refetch their queries once.
- Production logs a warning once per adapter when `secret` is missing.

Like `BETTER_AUTH_SECRET` or Auth.js's `AUTH_SECRET`, it is a server-only key that must match across instances. You can reuse your authentication library's secret, but a dedicated one can be rotated on its own.

### Adapter Factories And AOT

When constructing the adapter requires runtime services, pass a synchronous factory instead of an instance:

```ts
export const sync = {
  adapter: () => drizzleSyncAdapter({ db, namespace: "my-app" }),
  principal: ({ request }) => requireUser(request).id,
} satisfies FurinSyncOptions;
```

Furin calls the factory once when `furinSync(sync)` or `furin({ sync })` is composed, validates the adapter, secret and notifier, and shares that runtime between mutations, browser event transports, recovery and `invalidateSync`. Factory errors reject composition before `.listen()`. SQLite and PostgreSQL transaction types remain inferred from the factory's return value. Factories returning a promise are unsupported. Requests and `invalidateSync` never initialize a factory: compose a Sync plugin before using them.

During mount discovery and AOT compilation, Furin installs the same hooks, macros and routes without invoking the factory; Elysia attaches the compiled handlers to the real resources when the application starts. The factory does not suppress effects in imported modules, so guard service acquisition with Elysia's `inAotBuild()` in the module that owns it:

```ts
import { inAotBuild } from "elysia";

if (!inAotBuild()) {
  // Await the application's existing service acquisition and migrations here.
  // Assign its resources before composing the application and calling listen().
}
```

- If a dependency opens SQLite at import time, move that import inside the guarded block too.
- Read services inside handlers, factories and authentication callbacks, not while declaring them: routes and schemas must remain declarable without those resources.
- Do not use `onStart` to acquire resources that must be ready before the socket opens.
- The guard covers discovery and compilation only. SSG/ISR prerendering executes loaders normally and still requires their resources.

The application owns its database and service scope; Furin releases its event subscriptions without closing the borrowed database.

## Declare Synced Mutations

Install `furinSync(sync)` before the routes it owns:

```ts
// src/api/index.ts
import { Elysia, t } from "elysia";
import { furinSync } from "@teyik0/furin";
import { sync } from "../sync";
import { posts } from "../db/schema";

export const api = new Elysia({ prefix: "/api" })
  .use(furinSync(sync))
  .post(
    "/posts",
    { body: t.Object({ title: t.String() }) },
    ({ body, mutation, invalidate }) => mutation(tx => {
      invalidate({ tags: ["posts"] });
      return tx.insert(posts).values(body).returning().get();
    })
  );
```

Every non-`GET`/`HEAD`/`OPTIONS` route covered by the plugin participates in sync. A successful mutation invalidates the GET at its own URL; [`invalidate()`](#identify-reads-by-url) adds GET URLs, cache tags or pages.

With an ORM adapter, return `mutation(callback)` and perform all dependent reads and writes through its native, fully inferred `tx`:

- Furin reserves the idempotency key before running the handler. The native transaction locks and rechecks that reservation, then commits business writes, the replayable response and the journal entry together. Cache invalidation and notifications run after commit; the cache itself is outside the database transaction.
- A failed business result (`4xx`/`5xx`), exception, response-schema validation, serialization, lease check or journal write rolls back the entire transaction.
- Once PostgreSQL has checked and locked the reservation, that transaction keeps ownership until commit or rollback; another request cannot take over an expired lease meanwhile. The ORM's own transaction timeout still applies.
- The callback resolves to its real native value on the first execution, preserving Prisma dates and Drizzle types. A replay or idempotency conflict short-circuits the HTTP handler instead of fabricating an ORM value from JSON. Build the complete response in the callback and return its result directly: response-changing hooks and work after the callback are outside the transaction.
- Calls to the global database client and external side effects do not become transactional.

Drizzle supports `bun:sqlite` and `bun-sql` PostgreSQL. SQLite callbacks and response validators must be synchronous; PostgreSQL callbacks may be async. Atomic responses must be bounded JSON, text, or bodyless `Response` values such as redirects. Async PostgreSQL transactions also accept body-bearing `Response` values with an explicit `Content-Length` up to 1 MiB; Bun SQLite transactions require bodyless `Response` values.

### Prisma 7 with PostgreSQL

```ts
import { prismaSyncAdapter } from "@teyik0/furin/sync/prisma";
import { type FurinSyncOptions, PollingSyncNotifier } from "@teyik0/furin/sync";
import { prisma } from "./db";

const adapter = prismaSyncAdapter({ client: prisma, namespace: "my-app" });
export const sync = {
  adapter,
  // Distributed production runtimes require an explicit notifier.
  notifier: new PollingSyncNotifier(adapter, 250),
  principal: ({ request }) => requireUser(request).id,
} satisfies FurinSyncOptions;

// Inside an Elysia handler using furinSync(sync):
return mutation(tx =>
  tx.post.create({ data: body })
);
```

Run `@teyik0/furin/sync/postgres/migration.sql` (see [PostgreSQL](#postgresql)) on the same PostgreSQL database. Prisma 7 keeps its generated transaction client and model inference; the journal needs no custom Prisma models. Prisma 8 and other Prisma database providers are not supported. Drizzle PostgreSQL uses the same migration and also requires an explicit notifier in production.

### Opt Out Of Replay

Set `idempotent: false` for routes whose request or response cannot be replayed safely:

```ts
.post("/uploads", { idempotent: false }, uploadFile)
```

Such a route ignores `Idempotency-Key`, stores no response and cannot use `mutation()`: every request runs. Its invalidations still apply once it succeeds: caches are purged, the caller receives them, and they are journaled and broadcast. Their journal entries carry no principal, so other browsers refresh all their live reads rather than only the affected ones. Typical exclusions include uploads, downloads, streams, payment initiation, and handlers with deliberately non-repeatable external effects.

## Identify Reads By URL

A GET is identified by its URL: its route pattern and params (`/boards/:boardId/cards` with `{ boardId: "alpha" }`). The query string is ignored. Nothing is declared; keep database access inside the Elysia handler:

```ts
new Elysia().use(furinSync(sync))
  .get("/boards/:boardId/cards", ({ params }) => listCards(params.boardId))
  .post("/boards/:boardId/cards", {
    body: t.Object({ title: t.String() }),
  }, ({ params, body, mutation }) =>
    mutation(tx => createCard(tx, params.boardId, body.title))
  );
```

The server stamps every successful data GET with its URL identity and the principal's session in the `x-furin-query` response header. A successful mutation invalidates the GET at its own URL: `POST /boards/alpha/cards` refreshes `GET /boards/alpha/cards`, `PATCH /cards/c1` refreshes `GET /cards/c1`. A rollback publishes no invalidation.

To invalidate other resources, call `invalidate()` from the handler context:

| Call | Invalidates |
|---|---|
| `invalidate(pattern, params?)` | GETs matching a pattern; an omitted param matches every value (`invalidate("/boards/:boardId")` refreshes every board) |
| `invalidate({ tags: ["posts"] })` | Cached paths that declared those tags |
| `invalidate({ path: "/blog", type: "page" })` | One exact page path |
| `invalidate({ path: "/blog", type: "layout" })` | A path and its descendants |

Calls are additive, share the mutation's headers and journal entry, and are discarded unless the mutation succeeds or commits. Calls from hooks, such as a `guard()`'s `beforeHandle`, add up with the handler's:

```ts
.delete("/cards/:id", ({ params, mutation, invalidate, problem }) =>
  mutation((tx) => {
    const card = getCard(params.id, tx);
    if (!card) return problem("Not Found", { detail: "Card not found" });
    deleteCard(tx, params.id);
    invalidate("/boards/:boardId", { boardId: card.boardId });
    return { ok: true };
  })
)
```

In a `mutation()` route, call `invalidate()` before the callback returns: a later call throws in development and is ignored in production. Calling `invalidate()` while handling a `GET` throws.

Register the application once to type the patterns. They are the app's GET routes, prefix included; unknown routes, routes without a GET and wrong param names are type errors. Without a registered app, `invalidate()` accepts any path and params:

```ts
// src/api/index.ts
declare module "@teyik0/furin" {
  interface Register { app: typeof api }
}
```

### Invalidate Outside A Request

From a cron job or webhook consumer, call `invalidateSync()` with the same `sync` options and any target `invalidate()` takes. It purges the pages built from it, then journals and broadcasts the invalidation, as a mutation would. The adapter journals the change and the notifier wakes connected clients, including those served by other processes sharing the adapter:

```ts
import { invalidateSync } from "@teyik0/furin";
import { sync } from "./sync";

await invalidateSync(sync, "/api/boards/:boardId", { boardId });
await invalidateSync(sync, { tags: ["board-count"] });
await invalidateSync(sync, { path: "/board", type: "layout" });
```

Without principal provenance, clients recovering these entries perform a full reset. For a worker acting for a known, verified principal, pass explicit provenance to keep query invalidations targeted:

```ts
await invalidateSync(sync, "/api/boards/:boardId", { boardId }, { principal: ownerId });
await invalidateSync(sync, { tags: ["board-count"] }, { principal: ownerId });
```

The application determines `ownerId` in trusted server code; this option does not authenticate a user or grant access. SQLite, PostgreSQL and Redis store the principal hash in the existing journal column/field, so no migration is needed, and another principal never receives these tags or scopes. Mixed-principal pages, historical entries and custom adapters still produce a conservative full reset. Custom adapters receive provenance as the optional second argument of `SyncAdapter.appendInvalidations(invalidations, principal?)`, but persisting it does not opt them into the built-in provenance trust boundary: they still recover through resets.

## Call A Mutation

Register the `furinSync` Eden plugin on an ordinary Eden client. Mutations keep their arguments and typed `{ data, error }` results:

```ts
import { treaty } from "@elysia/eden";
import { furinSync } from "@teyik0/furin/client";
import type { Api } from "./server";

export const api = treaty<Api>(origin, { headers: auth }).use(furinSync).api;
// On the server (isomorphic code): treaty(serverApi).use(furinSync).api

const { data, error } = await api.posts.post({ title: "Hello" });
```

- A plain call stays a plain Eden call. Without a client key, the server generates one: the mutation still runs transactionally, invalidates and broadcasts, but a resend is not deduplicated.
- A call that passes an options object gets an automatic `Idempotency-Key` and the typed `optimistic` option. Each call gets a new key, even when calls share an options object, and the plugin never alters that object.
- Explicit keys are respected, including Eden header callbacks and `fetch.headers`. Never reuse an explicit key across sessions or principals.
- `x-furin-queries` invalidations in a mutation response refresh the client's live queries whether or not options were passed.
- Reads and subscriptions keep Eden behavior. The plugin requires Eden 2.0.0-rc.1 or later.

All Eden configuration (`fetcher`, headers, interceptors, date parsing and error behavior) stays on `treaty()`. Retries belong to [`useMutation`](#retry).

## Live Reads In Loaders

Every GET has a live query, `.get.live(options?)`, on a client using the `furinSync` Eden plugin. Await it in a loader to track the read:

```ts
export const route = defineRoute("/board/[boardId]")
  .config({ mode: "ssr" })
  .loader(async ({ params }) => {
    const { data, error } = await api.boards({ boardId: params.boardId }).cards.get.live();
    if (error) throw error;
    return { initialCards: data };
  });
```

No matching loader tag is needed: Furin registers the dependency of every completed live read, so cache tags and sync refreshes target the route. A plain `await api.…get()` stays an untracked Eden call.

Tracking does not forward the page request's authentication headers: keep credentials on the server-side Eden client request. Use SSR or request loaders for personalized reads; public SSG/ISR loaders must remain public.

The read's response body is sent to the browser, so `useQuery` and `cache.update` start from it without a GET, only when the loader output already exposes all of it by object identity: either the whole response (`return { initialCards: data }`) or every top-level field as an object or array (`return { board: data.board, cards: data.cards }`). Otherwise only the dependency travels and the browser fetches the GET when it needs it. A loader that reads `{ displayName, passwordResetToken }` and returns `displayName`, or returns `board` and `cards` but not a scalar `total`, never sends the rest of the response.

### Update Loader Props With One GET Projection

Keep objects and arrays from the GET in the loader result:

```tsx
.loader(async ({ params }) => {
  const { data, error } = await api.boards({ boardId: params.boardId }).get.live();
  if (error) throw error;
  return { board: data.board, cards: data.cards };
})
.page(({ cards }) => {
  const done = cards.filter(card => card.column === "done").length;
  return <Board cards={cards} done={done} />;
})
```

One projection then updates the shared GET cache and these loader props:

```ts
optimistic(cache) {
  cache.update(api.boards({ boardId }).get.live(), board => ({
    ...board,
    cards: board.cards.map(card =>
      card.id === cardId ? { ...card, column: "done" } : card
    ),
  }));
}
```

No `useQuery`, route target or second optimistic transform is required. Furin records object-reference paths before serialization, projects props from the shared snapshot and retains the confirmed loader values for rollback. Nested object properties and whole arrays are supported, including cached public loaders. Derive counts and filters in the page: copied objects, array-element selections and computed scalars do not carry automatic bindings. Use a [route snapshot target](#route-snapshot-targets) for those transformations.

The same mapping works for `requestLoader` and `defer()` fields after they resolve:

```tsx
.requestLoader(({ params }) => ({
  privateCards: api.boards({ boardId: params.boardId }).get.live().then(({ data, error }) => {
    if (error) throw error;
    return data.cards;
  }),
}))
.page(({ privateCards }) => (
  <Suspense fallback={<p>Loading cards…</p>}>
    <Await resolve={privateCards}>{cards => <Board cards={cards} />}</Await>
  </Suspense>
))
```

GET dependencies and bindings travel with each resolved field, so a slow sibling does not delay them. The prop stays a promise compatible with `Await` and React `use()`. A `cache.update` of the board GET updates these cards and rolls back on failure. Sync invalidations also refresh the affected route and expire its prefetched snapshot. Private reads remain request scoped and are not stored in the public PPR shell.

### Optional Query Subscriptions

```tsx
import { useQuery } from "@teyik0/furin/client";

function Cards({ boardId }: { boardId: string }) {
  const { data, error, isFetching } = useQuery(api.boards({ boardId }).cards.get.live());
  if (error) return <p>Could not load cards.</p>;
  return <ul>{data?.map(card => <li key={card.id}>{card.title}</li>)}</ul>;
}

function DoneCount({ boardId }: { boardId: string }) {
  const { data } = useQuery(api.boards({ boardId }).cards.get.live(), {
    select: cards => cards.filter(card => card.column === "done").length,
  });
  return <span>{data ?? 0} done</span>;
}
```

The hook returns `data`, `error` and `isFetching`. `select` derives a value from the shared data without changing its identity. Awaiting a live query, or calling `await api.…get()` directly, still returns Eden's original result and performs a request.

Query arguments remain inferred from the GET schema and are passed to `.live()`:

```tsx
useQuery(api.cards.get.live({ query: { boardId, column: "done" } }), {
  select: cards => cards.length,
});
```

Cache sharing and invalidation:

- Consumers of the same GET, query arguments and request options share one cache entry and fetch.
- Completed loader reads with only `query` options hydrate the default cache without an initial browser GET. Reads with explicit request options, such as authorization headers, keep their loader bindings and PPR metadata under an isolated, opaque seed identity; browser consumers fetch their own variant because the server's credentials cannot be assumed to match.
- An invalidation refreshes every cached query variant of that URL, whatever its query string. Other params remain separate unless the invalidation omits them.
- Client-wide defaults belong to that client's session: create a fresh client when authentication changes and remount the authenticated router (or perform a full navigation). Response session identities also clear data from a previous principal and reject its late responses.

## Mutation State In React

`useMutation` adds React state to an existing mutation without changing its arguments:

```tsx
import { useMutation } from "@teyik0/furin/client";
import { useRouter } from "@teyik0/furin/link";

function DeleteCard({ cardId }: { cardId: string }) {
  const router = useRouter();
  const remove = useMutation(api.cards({ id: cardId }).delete, {
    onSuccess: async () => {
      await router.navigate("/boards");
    },
  });

  return (
    <>
      <button disabled={remove.isPending} onClick={() => remove.mutate()}>
        Delete card
      </button>
      {remove.error ? <p>Could not delete the card.</p> : null}
    </>
  );
}
```

The hook returns `data`, `error`, `isPending`, `mutate`, `mutateAsync` and `reset`. `mutate` returns `void` and reports failures through `error` and the optional `onError` callback. `mutateAsync` resolves with the response's `data`, or rejects with the same error exposed to `onError` (including when `onError` itself throws).

### Errors

Every exposed error has Eden's `{ status, value }` shape, with `value.detail` guaranteed to be a string at runtime and in TypeScript:

- An API error whose object payload already contains a string `detail` is unchanged.
- Otherwise the hook creates an `EdenFetchError` that keeps the HTTP status and the inferred fields of object payloads and adds `detail`. A nonempty text body becomes the detail; empty, null, array or other primitive bodies use `"Mutation failed"`. The original error is kept in `cause`, unmodified.
- Network errors and other exceptions, including failures in `onSuccess` and Eden's synthetic errors without an HTTP response, become an `EdenFetchError` with `status: 0` and the exception's message (or `"Mutation failed"` for non-Error values) in `value.detail`. Status `0` is a client-side sentinel, not an HTTP status.

There is one error callback, with no separate native `Error` branch:

```tsx
const save = useMutation(api.cards({ id: cardId }).patch, {
  onError(error) {
    setErrorMessage(error.value.detail);
    // error.status === 0 distinguishes client-side exceptions when needed.
  },
});
```

Use `error.status` to narrow a specific response. The hook guarantees `detail`, not runtime validation of the other fields against the server's schema, and normalized messages are not localized. Direct Eden calls keep their native response contract.

### Concurrency

Calls run in parallel. `isPending` stays true until every call and its awaited `onSuccess` or `onError` callback finishes. Only the most recently started call publishes `data` or `error`; callbacks still run for each call. The hook does not deduplicate calls or provide a mutation lock, so disable the relevant controls while pending if the UI should prevent repeated submissions. `reset()` clears the displayed result and prevents earlier in-flight calls from publishing it again, but does not cancel those requests or their callbacks.

### Retry

Retry is a `useMutation` option. `retry: 2` means two additional attempts, three requests maximum. The default is `0`. The hook can also own the optimistic projection, which receives the `mutate()` arguments:

```tsx
const save = useMutation(api.cards({ id: cardId }).patch, {
  retry: 2,
  optimistic(cache, { title }) {
    cache.update(api.cards({ id: cardId }).get.live(), card => ({ ...card, title }));
  },
});

save.mutate({ title });
```

- Each `mutate()` call generates one `Idempotency-Key`. Only `409 FURIN_MUTATION_IN_PROGRESS` is retried, and every attempt reuses that key and one optimistic contribution.
- Furin respects `Retry-After`; otherwise it uses exponential delays. Cancellation stops waiting.
- Business errors, payload mismatch, lost leases, server errors, and network failures are never blindly retried. The client keeps this conservative policy even when an ORM adapter makes the server write atomic.
- Given an Eden method, the hook always passes an options object, so the plugin attaches the key. Given a function, the key attaches only if the function calls an Eden method synchronously with an options object, for example `(title) => api.cards({ id }).patch({ title }, {})`. Otherwise that call is not retried and development builds warn.

A missing response does not prove the domain write failed. After an ambiguous outcome, the optimistic view remains until loader revalidation reconciles it. The hook returns the Eden result; revalidation is automatic and the router reports its failures separately.

### External APIs

The hook does not require an Eden client. Any asynchronous function returning `{ data, error }` works, with `error: null` indicating success:

```tsx
async function deleteExternalCard(cardId: string) {
  const response = await fetch(`/external-api/cards/${encodeURIComponent(cardId)}`, {
    method: "DELETE",
  });
  if (!response.ok) {
    return { data: null, error: new Error("Could not delete the card") };
  }
  return { data: null, error: null };
}

const remove = useMutation(deleteExternalCard);
// remove.mutate(cardId)
```

This supplies mutation state and callbacks, not Furin Sync integration: an external API needs its own cache refresh strategy unless it implements the Sync protocol. Furin's page server still uses Elysia; the business API does not have to.

## Optimistic Updates

Inside an `optimistic(cache)` option, `cache.update(target, transform)` projects a change onto a loaded GET or route snapshot; `cache.update()` and `optimistic()` return `void`. The same rules apply to every target:

- A cache miss is a no-op.
- Transforms must be pure: Furin reapplies them over confirmed data. Generate temporary IDs and timestamps before the call.
- Each mutation owns its contribution. A definitive rejection removes only that contribution; success keeps it until fresh data replaces it.
- Reads and revalidations racing pending writes cannot apply an insert or increment twice: revalidation of a projected snapshot waits for its local requests to settle, while navigation to other snapshots stays available. Concurrent writes to the same entity still require an application policy such as version checks or serialization.
- Awaiting the mutation waits for its Eden response, not the final query/loader refresh.

### Reuse A Mutation And Its Optimism

Use an ordinary application function to centralize the API call and its projection:

```ts
// src/mutations/cards.ts
export function completeCard(boardId: string, cardId: string) {
  return api.cards({ id: cardId }).patch({ column: "done" }, {
    optimistic(cache) {
      cache.update(api.boards({ boardId }).cards.get.live(), cards =>
        cards.map(card => card.id === cardId ? { ...card, column: "done" } : card)
      );
    },
  });
}

// Any button, menu or keyboard shortcut:
await completeCard(boardId, cardId);
```

The list and its selected count update together. For a filtered GET, target the same arguments:

```ts
cache.update(
  api.cards.get.live({ query: { boardId, column: "done" } }),
  cards => cards.filter(card => card.id !== cardId)
);
```

Different endpoints remain different representations. Update each loaded representation explicitly when both should change immediately:

```ts
optimistic(cache) {
  cache.update(api.cards({ id: cardId }).get.live(), card => ({ ...card, title }));
  cache.update(api.boards({ boardId }).cards.get.live(), cards =>
    cards.map(card => card.id === cardId ? { ...card, title } : card)
  );
}
```

Furin does not normalize entities or execute relational live queries. Tags remain the lower-level mechanism for non-Eden reads and writes outside the mutation plugin. Shared public page caches only store a render after its discovered query dependencies were covered by its cache lease; the first dependency-discovery render may be served with `no-store`.

### Route Snapshot Targets

Target a route pattern to update the loader snapshot already rendered by the router:

```tsx
const { error } = await api.cards({ id: cardId }).patch(
  { column: "done" },
  {
    optimistic(cache) {
      cache.update("/board/:boardId", (loader) => ({
        ...loader,
        initialCards: loader.initialCards.map((card) =>
          card.id === cardId ? { ...card, column: "done" } : card
        ),
      }));
    },
  }
);
```

The page keeps rendering its `initialCards` loader prop: no copied `useState(initialData)`, setter, rollback callback, or manual synchronization is needed. The generated `RouteMap` offers route completion and infers loader fields from the target; generate `furin-env.d.ts` before using typed targets. A route pattern updates only the active loaded snapshot for that route, whatever its path and query parameters, and the transform returns complete loader data for that route. A successful response keeps its contribution until fresh loaders replace it in the same router publication. Optimistic mutations revalidate automatically even with `autoRefresh: false`. Loaders must read committed writes; Furin cannot establish that guarantee for an eventually consistent replica or external service.

To target an exact query snapshot rather than the active route, use a typed URL target:

```ts
cache.update({ path: "/posts", search: { category: "news" } }, (loader) => ({
  ...loader,
  posts: loader.posts.filter((post) => post.id !== deletedId),
}));
```

## Subscriptions Outside React

### Remote Client

Use `@teyik0/furin/sync/client` in a Bun desktop process or another runtime with Fetch, WebSocket and AbortController support. This entrypoint imports neither React nor server adapters and needs no DOM or router. It exports the same Eden `furinSync` plugin as `@teyik0/furin/client`.

`await api.state.get.live()` remains a single Eden request. Creating a sync client or observing its connection state opens nothing. `subscribe()` starts a persistent connection; `reconnect()` explicitly restarts it.

Here is a complete Bun client for a remote Furin application whose exported `App` type includes `GET /state` returning `{ value: number }`. Import that type only; the server is not executed in the desktop process. The server must configure `furin({ sync })` and authenticate both reads and `sync.principal`.

```ts
// follow-state.ts — run with bun follow-state.ts
import { treaty } from "@elysia/eden";
import {
  createSyncClient,
  furinSync,
  SyncClientError,
} from "@teyik0/furin/sync/client";
import type { App } from "./server";

const url = process.env.FURIN_SERVER_URL;
let token = process.env.FURIN_ACCESS_TOKEN;
if (!url || !token) throw new Error("Set FURIN_SERVER_URL and FURIN_ACCESS_TOKEN");

const headers = () => ({ authorization: `Bearer ${token}` });
const api = treaty<App>(url, { headers }).use(furinSync);

// Bun accepts upgrade headers. The overload also works in projects loading lib.dom types.
const BunWebSocket = WebSocket as typeof WebSocket & {
  new (url: string, options: { headers: Headers }): WebSocket;
};
const client = createSyncClient({
  url,
  headers,
  createWebSocket: (address, upgradeHeaders) =>
    new BunWebSocket(address, { headers: upgradeHeaders }),
});

const stopConnection = client.subscribeConnection(({ status, error }) => {
  console.log("Sync:", status, error?.status);
  if (status === "unauthorized") {
    // Ask your authentication service for renewed credentials, or sign out.
    // Same identity and access scope: token = renewedToken; client.reconnect({ preserveCache: true });
    // New identity or permissions: token = renewedToken; client.reconnect();
  }
});

const stop = client.subscribe(api.state.get.live(), ({ data, error, isFetching }) => {
  if (error instanceof SyncClientError) {
    console.error("Read transport failed:", error.cause);
  } else if (error) {
    // Eden's inferred error union is preserved: narrow error.status for typed error.value.
    console.error("GET failed:", error.status, error.value);
  } else if (data && !isFetching) {
    console.log("New value:", data.value); // number, inferred from App
  }
});

const shutdown = Promise.withResolvers<void>();
const onSignal = () => shutdown.resolve();
process.once("SIGINT", onSignal);
process.once("SIGTERM", onSignal);
try {
  await shutdown.promise;
} finally {
  process.removeListener("SIGINT", onSignal);
  process.removeListener("SIGTERM", onSignal);
  stop();
  stopConnection();
  client.close();
}
```

Lifecycle:

- All subscriptions of one client share its socket, journal cursor and query cache. Identical reads from the same Eden client share a fetch.
- `subscribe()` immediately delivers the cached snapshot, then reports data, typed Eden errors and fetching changes. Stopping a subscription removes its observer; the client keeps its connection for reuse until `close()`.
- `close()` is idempotent: it removes listeners, closes the socket, cancels reconnect/reset timers, aborts owned HTTP requests and releases the cache. Late responses cannot restore it, even if a fetch adapter ignores cancellation.
- The first read waits until the server has installed notification delivery and journal recovery has completed. Invalidations arriving during a read are coalesced and cause a subsequent read. Network reconnections preserve the cursor and catch up from the journal. Browser query subscriptions use the same query store and recovery engine; the router additionally invalidates page and loader snapshots.

Options:

- Configure one client per Furin application URL and authentication context. `url` includes the application's mount path, for example `https://example.com/desktop`. For a server configured with `sync.path: "/internal/sync"`, pass `syncPath: "/internal/sync"`; it is resolved under that mount path. A query from another origin is rejected.
- `headers` accepts a value or an async callback, applied to recovery and subscribed Eden reads. Keep the Eden configuration consistent for one-shot reads and mutations too; explicit Eden `fetch.headers` and `onRequest` hooks must not override that context with different credentials. Do not mix per-query credentials from different principals within a client.
- `fetch` accepts standard request settings such as `credentials: "include"`, used for recovery and subscribed reads. `fetcher` customizes recovery HTTP requests; live reads keep their Eden fetcher.
- With explicit headers, `createWebSocket` is required so credentials reach the upgrade too. The factory only constructs a runtime socket; it does not implement Furin's protocol. Browser cookie authentication can use the native WebSocket without a factory. Node.js 22+ can use the built ESM entrypoint with a WebSocket adapter supplied by the host for authenticated upgrades; Furin adds no socket dependency and provides no cookie jar.
- The remote client targets the Bun server WebSocket transport, not Vercel's SSE transport.

Connection state: `getConnectionState()` returns `{ status, error, reason? }` and `subscribeConnection()` observes changes. Status is `idle`, `connecting`, `connected`, `reconnecting`, `unauthorized` or `closed`.

- HTTP 401/403 from recovery or event authentication, and HTTP 401 from a subscribed GET, stop automatic reconnection (`unauthorized`).
- A query's HTTP 403 is a resource denial: its typed Eden error is delivered and its cached data removed, while other subscriptions continue.
- Other connection failures retry with bounded exponential backoff.
- WebSocket APIs can hide an upgrade's HTTP status. Recovery is checked over HTTP first, but an upgrade-only rejection cannot always be classified by a generic socket; an adapter that can inspect that rejection should reject with `new SyncClientError(message, 401)` or `403`. Applications do not handle Furin's socket close codes.

### In-Process Subscriptions

When the consumer and the Elysia application share a Bun process, use `createLocalSyncClient` from the server entrypoint. It returns the same `SyncClient` as `createSyncClient`, so subscriptions, connection state, credential changes and shutdown use the same API:

```ts
import { treaty } from "@elysia/eden";
import { createLocalSyncClient } from "@teyik0/furin/sync";
import { furinSync } from "@teyik0/furin/sync/client";
import { app, sync } from "./server";

const api = treaty(app).use(furinSync);
const client = createLocalSyncClient({ app, sync });

// A normal typed Eden result; no subscription is opened.
const initial = await api.state.get.live();

const stop = client.subscribe(api.state.get.live(), ({ data, error }) => {
  if (error) console.error(error);
  else if (data) console.log(data.value);
});

// During application shutdown:
stop();
client.close();
```

- Pass the original, composed Elysia application to both `treaty(app)` and `createLocalSyncClient`. A live query from another application or a URL-based Eden client is rejected, even if the synthetic origins match.
- Use the same `sync` configuration as the server. Its recovery endpoint must be installed by `furin({ sync })` or, for standalone Elysia, `createSyncChangesPlugin(sync)`. The factory neither registers routes nor starts a listener, and works before or after the application starts listening. Application services and their startup/shutdown stay owned by the host; if startup is host-controlled, import the application from a module that guards `.listen()` with `import.meta.main`.
- The transport receives cursor notifications from the server coordinator and executes recovery requests through `app.handle()`; live reads keep Eden's in-process dispatch. No HTTP connection, socket, DOM or React runtime is required, and one notifier subscription is shared across queries. Durable adapters and distributed notifiers can still contact their own database or service.
- `syncPath` overrides the recovery base path within the composed app. For an application mounted under `/desktop`, pass `syncPath: "/desktop/_furin/sync"` if that is where the endpoint is registered. Otherwise it defaults to `sync.path` or `/_furin/sync`. No URL or WebSocket factory is needed.

Local dispatch does not invent a principal or bypass application authorization: reads and recovery run through the application's handlers. If authentication uses request headers, share the same request configuration:

```ts
const request = {
  headers: () => ({ authorization: `Bearer ${token}` }),
};
const api = treaty(app, request).use(furinSync);
const client = createLocalSyncClient({ app, sync, ...request });

// After replacing the credentials:
client.reconnect();
```

Per-query request overrides must stay consistent with that authentication context, as for the remote client. Local clients acquire the optional [connection-validity hook](#connection-validity) through an authorized `app.handle()` request, once per connection, using the real Elysia context.

### Credentials And Reconnection

Use one dynamic `headers` callback as the credential provider for Eden and Sync. It may await your application's token acquisition or renewal and is called for authentication, recovery and subscribed reads. Furin imposes no JWT, token storage, auth SDK or React hook. With HttpOnly cookies, omit explicit headers in the browser: Fetch and the same-origin event transport send the cookie without exposing it to JavaScript. A Bun host supplies its own cookie jar if it needs one.

The client cache is memory owned by that `SyncClient` and shared by its observers. While a connection restarts, its state carries `reason: "network" | "credentials" | "context"`; `reason` is absent once connected.

- **Network reconnect** (`network`): keeps snapshots and the journal cursor. Recovery stays targeted, and interrupted reads are retried.
- **`client.reconnect({ preserveCache: true })`** (`credentials`): renews credentials for the same user, tenant and access scope. It keeps snapshots and the cursor, cancels and fences old reads, then reevaluates active queries. Inactive snapshots stay stale until subscribed again; kept values remain visible while their replacement loads.
- **`client.reconnect()`** (`context`): the conservative action for permission, user or tenant changes. It immediately clears all snapshots and the cursor, fences old reads, reauthenticates and reloads active queries. It does not erase the application's own copies of earlier values.
- Recovery identifies the server-verified principal with an opaque hash. A different principal forces a clear even if cache preservation was requested. Include the tenant in the principal when tenants are distinct access contexts; Furin cannot infer tenant or permission boundaries the application omits.
- A global authentication refusal clears snapshots and pauses automatic attempts until the application calls `reconnect()`. The provider can also reject with `SyncClientError(message, 401)` or `403` when credentials are definitively unavailable. A resource's 403 is not a global refusal.

The application owns token refresh and its retry policy; Furin does not silently retry an authorization denial. Call `reconnect()` explicitly after changing credentials or identity, rather than changing a header callback's principal while its old socket stays connected.

In the browser, the built-in transport checks authentication over HEAD using same-origin cookies before connecting. After a global refusal and a successful application cookie refresh, `router.refresh()` resumes Sync; a full navigation also starts a new runtime. A context change invalidates query and loader caches, cancels pending navigations and deferred transports, and prevents old navigation results from publishing even when cancellation is ignored. New-context refreshes do not wait for those obsolete requests. Current loaders refresh according to `autoRefresh`. User or tenant switches in a router application still require a fresh authenticated router or full navigation.

### Connection Validity

Authentication is checked when opening the event connection and on each HTTP recovery/read. For a permission change, expiry or revocation that produces no Sync mutation, optionally associate a validity lease with the authenticated event connection:

```ts
import type { FurinSyncOptions } from "@teyik0/furin/sync";

const sync = {
  adapter,
  principal: async context => (await auth.requireSession(context)).principal,
  connection: async context => {
    // Application service: a fresh watch for revocation or permission changes.
    const watch = await auth.watchSession(context);
    const expired = new AbortController();
    const remaining = watch.expiresAt - Date.now();
    const timer = remaining > 0
      ? setTimeout(() => expired.abort(), remaining)
      : undefined;
    if (remaining <= 0) expired.abort();
    return {
      signal: AbortSignal.any([watch.signal, expired.signal]),
      release: () => {
        clearTimeout(timer);
        watch.release();
      },
    };
  },
} satisfies FurinSyncOptions;
```

`auth` here is your service: it validates credentials, provides a principal, and exposes a fresh `{ signal, expiresAt, release }` watch. Furin does not implement those rules. Omitting `connection` acquires no validity resource.

- The hook runs once per authenticated WebSocket, SSE or local event connection, not per query, recovery request or SSR loader.
- Furin observes an already-aborted signal immediately and calls the returned `release()` exactly once on normal closure, interrupted validity, failed opening or late asynchronous acquisition after closure. A release exception is logged and cleanup continues. If the hook throws before returning a lease, it must release its partially acquired resources itself.
- An aborted signal means **reauthenticate**, not **permanently denied**. Furin discards the old access snapshots, fences in-flight reads and recovers using current credentials, even if the journal cursor has not changed. Because the signal does not distinguish expiry from changed permissions, this path conservatively clears snapshots; renew with `reconnect({ preserveCache: true })` before expiry when the access context is known to be unchanged. Repeated interrupted leases use bounded retry delays; a 401/403 during connection authentication stops retries. Supply a fresh signal after reauthentication.

Without this hook, an open, silent connection cannot detect a revocation by itself. With it, timely detection depends on the application delivering the signal, across server processes when needed. The signal is not a durable journal entry: a permission change missed while disconnected needs an explicit `reconnect()` or an access revision represented in the principal. Furin cannot retract values already copied outside its cache, and roles, revoked devices or file permissions remain application logic. Every query and mutation must still enforce its own authorization; the lease never grants resource access. As with browser sync, notifications invalidate snapshots: subscribers receive current query values, not a lossless stream of every intermediate business event.

## Replay Semantics

The adapter keys a mutation by principal, method, pathname, and idempotency key, and fingerprints its payload.

| Situation | Result |
|---|---|
| First request | Acquires a lease and runs the handler |
| Same key and same request after success | Replays the stored response |
| Same key while the first request is running | `409 FURIN_MUTATION_IN_PROGRESS`; retrying after it completes replays its response |
| Same key with a different payload | `409 FURIN_IDEMPOTENCY_MISMATCH` |
| Missing key | Runs with a server-generated key; not deduplicated |
| Invalid key | `400 FURIN_INVALID_IDEMPOTENCY_KEY` |
| Unsupported request body | `415 FURIN_UNSUPPORTED_SYNC_BODY` |
| Lost mutation lease before commit | `503 FURIN_SYNC_LEASE_LOST` |

Only successful `2xx` and `3xx` results are committed. Stored bodies are limited to 1 MiB; hop-by-hop, authentication, and cookie headers are excluded from replay. ORM adapters roll back unreplayable results before commit.

The standalone `sqliteSyncAdapter`, `postgresSyncAdapter` and `redisSyncAdapter` keep a separate handler/receipt lifecycle. They store the receipt and journal atomically, but cannot include writes made through an independent domain connection. Their bounded `Response` support requires a valid `Content-Length`; an unreplayable successful result is stored as a safe framework error. Use an ORM adapter plus `mutation(tx => ...)` for atomic domain writes. Furin cannot make a third-party API call exactly once.

## Browser Catch-Up

After a commit, the notifier wakes connected browsers with the latest cursor. The client then reads ordered pages from the `/_furin/sync/changes` recovery endpoint, invalidates prefetched routes, and refreshes the active route when affected.

Built-in adapters return paginated changes attributable to the current principal. If recovery crosses another principal's changes, older entries without principal provenance, or a custom adapter without that provenance, Furin invalidates all cached queries and prefetched routes instead of exposing journal scopes. With `autoRefresh: true`, it also reloads the active route's loaders; with `autoRefresh: false`, they refresh on the next navigation or an explicit router refresh.

Bursts of commits are coalesced: each server process wakes its browsers at most once per 100 ms, always with the latest cursor, and each browser runs a reset-driven full refresh at most once per second. Both limits fire on the trailing edge, so the final state is always fetched.

The wake-up transport is best-effort. Correctness comes from the durable adapter journal and cursor catch-up, so a missed browser event or notifier outage delays discovery but does not lose committed changes.

On Bun servers, sync, development diagnostics, and DevTools share one versioned `/_furin/events` WebSocket per page. The Vercel adapter streams sync notifications over Server-Sent Events through its HTTP handler. The browser reconnects when the event stream closes and catches up through the journal. Use the `furinSync` Eden plugin and the router rather than either internal endpoint.

## Adapter Choice

| Deployment | Adapter |
|---|---|
| Local tests or disposable development process | SQLite `:memory:` |
| One durable host | File-backed SQLite |
| Multiple replicas with PostgreSQL | PostgreSQL (recommended) |
| Redis as the durable sync store | Redis |
| PostgreSQL durability with faster wake-ups | PostgreSQL plus Redis notifier |

Production rejects process-local adapters such as SQLite `:memory:`. In development, Furin polls the adapter cursor when no notifier is configured; production with a distributed adapter (PostgreSQL, Redis, Prisma, Drizzle PostgreSQL) requires an explicit notifier.

### PostgreSQL

Apply the bundled idempotent schema bootstrap through the CLI or your migration system, including when upgrading an existing database: the journal's nullable `principal_hash` column is added without changing existing entries, which then use the full-refresh recovery path.

```sh
FURIN_SYNC_POSTGRES_URL=postgres://... \
  bunx --package @teyik0/furin furin-sync-postgres-migrate
```

```ts
import { SQL } from "bun";
import { postgresSyncAdapter, postgresSyncNotifier } from "@teyik0/furin/sync/postgres";

const sync = {
  adapter: postgresSyncAdapter({
    namespace: "my-app",
    sql: new SQL(databaseUrl),
  }),
  notifier: postgresSyncNotifier({
    namespace: "my-app",
    sql: new SQL(directDatabaseUrl),
  }),
  principal: ({ request }) => requireUser(request).id,
} satisfies FurinSyncOptions;
```

Use a direct PostgreSQL connection for the notifier's `LISTEN`; a transaction pooler may drop immediate notifications. Furin checks the durable cursor every 15 seconds to recover missed wake-ups. The adapter's SQL connection may use a pooler.

### Redis Notifier

Redis is another option for immediate wake-ups across replicas:

```ts
import { RedisClient, SQL } from "bun";
import { postgresSyncAdapter } from "@teyik0/furin/sync/postgres";
import { redisSyncNotifier } from "@teyik0/furin/sync/redis";

const sync = {
  adapter: postgresSyncAdapter({ namespace: "my-app", sql: new SQL(databaseUrl) }),
  notifier: redisSyncNotifier({
    client: new RedisClient(redisUrl),
    namespace: "my-app",
  }),
  principal: ({ request }) => requireUser(request).id,
} satisfies FurinSyncOptions;
```

The notifier carries cursors only. The adapter remains the source of truth.

## Lower-Level Alternative

Use `furinInvalidate()` for the same handler `invalidate()` without idempotency or a change journal: a successful mutation purges the server caches built from its targets and its own URL, and only the initiating response reports them (`X-Furin-Revalidate`, `x-furin-queries`). See [API Routes](/docs/api-routes#invalidation-after-a-mutation). Use Furin Sync when retries and cross-client catch-up are part of the mutation contract. See [Caching](/docs/caching) for the cache layers themselves.
