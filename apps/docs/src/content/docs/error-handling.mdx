# Error Handling

Furin separates unexpected failures from expected missing content:

- An error boundary catches loader and render failures.
- A not-found boundary handles unmatched URLs and `notFound()` from a loader.

How you declare them follows the app's [routing style](/docs/routing):

| | `nextjs` | `tanstack` |
|---|---|---|
| Error boundary | `error.tsx` default export | `.error(Component)` on the route |
| Not-found boundary | `not-found.tsx` default export | `.notFound(Component)` on the route |
| Scope | the directory, inside its layout | the route, in its parent's outlet |
| App-wide boundary | `error.tsx` / `not-found.tsx` at the top | `.error()` / `.notFound()` on `__root.tsx` |

The nearest authored boundary wins, and a boundary failure bubbles to the next parent boundary. Both styles share the components' props, the error normalization and the rendering rules below.

These page conventions return HTML or Furin's navigation transport. For JSON APIs, use Elysia 2's `problem()` and class-based `.onError(ErrorClass, handler)` APIs so failures follow RFC 9457 and Eden can infer each error response:

```ts
import { Elysia } from "elysia";

class PostUnavailable extends Error {}

export const postsApi = new Elysia()
  .onError(PostUnavailable, ({ problem }) =>
    problem(503, { detail: "Posts are temporarily unavailable" })
  )
  .get("/posts/:id", ({ params, problem }) => {
    if (!postsService.isAvailable()) throw new PostUnavailable();
    const post = findPost(params.id);
    return post ?? problem("Not Found", { detail: "Post not found" });
  });
```

Expected API failures use `application/problem+json`. Furin page `notFound()` remains a render-control signal rather than an API error, so it intentionally keeps the nearest `not-found.tsx` behavior.

## Error Boundaries

```tsx
// src/app/blog/error.tsx
import type { ErrorProps } from "@teyik0/furin";

export default function BlogError({ error, reset }: ErrorProps) {
  return (
    <section role="alert">
      <h1>Blog unavailable</h1>
      <p>{error.message}</p>
      <small>Error ID: {error.digest}</small>
      <button onClick={reset}>Try again</button>
    </section>
  );
}
```

| Field | Meaning |
|---|---|
| `error.message` | Safe public message chosen by Furin's error normalization |
| `error.digest` | Deterministic 10-character hexadecimal correlation ID |
| `error.status` | HTTP status; thrown Responses and Eden problems retain their status, while other errors become `500` |
| `reset()` | Clears the client boundary and reloads the current route; it is a no-op during server rendering |

Thrown `Error` messages are not exposed directly. Ordinary failures become `Something went wrong`; the complete error and matching digest stay in server logs. A deliberately thrown `Response` may supply a public body and status. Throwing an Eden error whose value is an Elysia Problem Detail preserves its HTTP status and uses the problem's `detail` (or `title`) as the public message:

```ts
const { data: content, error } = await api().content.get();
if (error) throw error;
return { content };
```

The nearest error boundary handles this failure, including a 404 API response. Use `notFound()` when the page itself should render its not-found boundary. Failed renders are never cached; see [SPA And Cached Routes](#spa-and-cached-routes).

Without an authored boundary, Furin renders its built-in safe error screen inside the root layout. If the root document itself cannot render, a framework-owned minimal document is the last resort.

## Boundary Scope

**Next.js style.** A directory's `error.tsx` and `not-found.tsx` render inside that directory's layout. They handle failures of the directory's pages and deeper layouts, but not of the layout beside them: when `blog/layout.tsx` fails, the boundary in the parent directory handles it. This is the `error.tsx` scope of the Next.js App Router.

**TanStack style.** A route's `.error()` and `.notFound()` render in place of that route, inside its parent layout, as `errorComponent` and `notFoundComponent` do in TanStack Start. They handle failures of the route itself and of every route below it that declares no boundary of its own: a layout's `.error()` also catches the layout's own loader failure, and a page's `.error()` renders inside the page's layout. The root's `.error()` and `.notFound()` are the app-wide boundaries.

| What failed | What renders |
|---|---|
| A page loader, `head()` or `notFound()` in a page | The nearest boundary, inside every layout above it |
| A layout loader | The nearest boundary in a parent directory, inside the layouts above it |
| The root loader, or the document shell during rendering | The root boundary inside the framework's minimal document |

The root boundary also handles any failure that no deeper boundary declares, inside the root layout. A shell render failure cannot be traced to one segment, so the server and the client both render it as a root failure.

The layouts that stay rendered keep their loader data. Furin does not rerun their loaders, and failed loaders and their descendants do not contribute data. Hydration and client navigation render the same tree as the server. For an unmatched URL, a root layout that depends on an unexecuted loader is skipped.

## Not Found

```tsx
// src/app/blog/not-found.tsx
import type { NotFoundProps } from "@teyik0/furin";

export default function BlogNotFound({ error }: NotFoundProps) {
  return (
    <section>
      <h1>Post not found</h1>
      <p>{error.message}</p>
    </section>
  );
}
```

Trigger it from a loader when the URL matches a page but its resource does not exist:

```tsx
// src/app/blog/[slug]/page.tsx
import { defineRoute, notFound } from "@teyik0/furin";
import { t } from "elysia";

export const route = defineRoute("/blog/$slug/")
  .config({
    mode: "ssr",
    params: t.Object({ slug: t.String() }),
  })
  .loader(async ({ params }) => {
    const post = await getPost(params.slug);
    if (!post) {
      notFound({
        data: { slug: params.slug },
        message: "This post does not exist.",
      });
    }
    return { post };
  })
  .page(({ post }) => <Post value={post} />);
```

`notFound()` never returns. It selects the nearest not-found boundary, carries serializable `message` and `data`, and produces status `404`. The root not-found boundary (`src/app/not-found.tsx`, or `.notFound()` on `__root.tsx`) also handles URLs that match no page.

## Boundary Placement

```text
src/app/
├── error.tsx
├── not-found.tsx
├── layout.tsx
└── blog/
    ├── error.tsx
    ├── not-found.tsx
    ├── layout.tsx
    └── [slug]/page.tsx
```

Use root boundaries for the whole application and add deeper ones only where the UI or recovery action is meaningfully different.

## TanStack-Style Boundaries

In the TanStack style, `error.tsx` and `not-found.tsx` are ordinary routes (`/error`, `/not-found`). Chain `.error()` and `.notFound()` on the route instead, at any stage before `page()` or `layout()`:

```tsx
// src/routes/blog/route.tsx
import { defineRoute, type ErrorProps, type NotFoundProps } from "@teyik0/furin";

function BlogError({ error, reset }: ErrorProps) {
  return (
    <section role="alert">
      <p>{error.message}</p>
      <button onClick={reset}>Try again</button>
    </section>
  );
}

function BlogNotFound({ error }: NotFoundProps) {
  return <h1>{error.message}</h1>;
}

export const route = defineRoute("/blog")
  .config({ mode: "ssr" })
  .error(BlogError)
  .notFound(BlogNotFound)
  .layout(({ children }) => <section className="blog">{children}</section>);
```

The components receive the same `ErrorProps` and `NotFoundProps` as `error.tsx` and `not-found.tsx`. `notFound()` from `blog/$slug.tsx` renders `BlogNotFound` in place of the blog layout, inside the root document; give the page its own `.notFound()` to render inside the blog layout instead. Declare the app-wide boundaries on `__root.tsx`:

```tsx
// src/routes/__root.tsx
export const route = defineRootRoute()
  .config({ mode: "ssr" })
  .error(AppError)
  .notFound(AppNotFound)
  .layout(({ children }) => <Document>{children}</Document>);
```

The [route config checks](/docs/routing#route-config-checks) report `.error()` and `.notFound()` in a Next.js-style app, where boundaries are files.

## Redirects And Responses

Loaders may throw an HTTP redirect `Response` whose status is `301`, `302`, `303`, `307`, or `308` and which includes `Location`. Furin forwards it as navigation. A redirect status without `Location` is treated as an error because it is not a valid navigation response.

## SPA And Cached Routes

SPA navigation uses the same nearest boundaries as the initial server request. Missing routes and loader `notFound()` results render inline without replacing the document.

SSG and ISR do not cache failed renders. An ISR miss that fails returns the error response with `no-store`, leaves the previous cache state untouched, and lets a later request try again. If a streaming failure happens after headers have been flushed, the UI can still switch to a boundary but the original HTTP status can no longer change.
