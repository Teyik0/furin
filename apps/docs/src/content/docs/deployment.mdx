# Deployment

Furin provides deployment targets for Bun, Vercel, Cloudflare Workers, and static hosting. Railway, Fly.io, Render, and self-hosted Docker deployments share the Bun server bundle; they do not need separate runtime adapters. Compiled executables remain optional. The `package` output composes a page tree into another Elysia application.

## Choose An Output

| Requirement | Recommended output |
|---|---|
| Vercel Functions, CDN assets, and native ISR | Vercel Build Output |
| Cloudflare Workers SSR/SSG with native CDN assets | Cloudflare Workers target |
| SSR, ISR, APIs, or Sync in a normal Bun environment | Bun server bundle |
| Small operational artifact with assets mounted beside it | Compiled `server` |
| One distributable executable | Compiled `embed` |
| Only SSG pages and no request runtime | Static export |
| Publish a Furin app for another Elysia host | Package target |

Choose Cloudflare Workers only when the application and its dependencies are compatible with the Workers runtime. Bun remains the build tool, not the deployed runtime on that target. ISR, PPR, RSC, and Sync are not supported by the initial Workers target and fail the build explicitly. Node.js is not a build target.

For a managed Bun host, start with [Railway](#railway). For containers, use the same [Docker image](#docker-server-bundle) on [Fly.io](#flyio), [Render](#render), or [a self-hosted server](#self-hosting-and-coolify). All of these can put a CDN in front of browser assets without compiling the server to an executable.

## Elysia 2 / Kiana Migration

Furin pins the Elysia 2 beta line and its matching official packages. Existing applications should run the official codemod first, then let TypeScript expose the Furin-specific integration points:

```sh
bunx @elysia/codemod@latest
bun add elysia@2.0.0-beta.21 @elysia/eden@2.0.0-beta.5 @elysia/static@2.0.0-beta.2 typebox@1.3.34 exact-mirror@1.2.6
```

`typebox` and `exact-mirror` are direct application dependencies because Kiana declares them as peers rather than embedding private copies. This keeps one compatible validator/normalizer graph for Elysia, its plugins, Eden, and Furin; `typebox` is also part of Furin's public schema contract. Exact Mirror itself contributes only a small runtime module—the larger compiled-binary increase in this beta comes primarily from the TypeBox 1 runtime and Bun bytecode amplification.

The important manual checks are:

- route arguments are now `(path, hooks, handler)`;
- lifecycle registration drops the `on` prefix (`beforeHandle`, `afterHandle`, `error`, `request`, and `afterResponse`);
- lifecycle scope `scoped` is now `plugin`;
- official plugins move from `@elysiajs/*` to `@elysia/*`;
- TypeBox 1 uses the `typebox` package;
- WebSocket support is explicit through `elysia/websocket`.

See the official [Elysia 2 DayDream release post](https://elysiajs.com/blog/elysia-20) for the complete breaking-change list.

Furin automatically enables `elysia/plugin/aot/bun` for Bun server bundles, compiled executables, and Vercel Bun Functions. Applications using `.mount()` skip AOT because Elysia's AOT plugin cannot compile mounted handlers; beta.19 bundles its runtime TypeBox dependencies without Furin's former setup shim. It generates a real, listener-free application entry for Elysia's dry run and keeps the boot entry separate. Runtime compiler stripping stays on `auto`: Furin completes the export surface of Kiana's no-WebSocket stub while preserving its throwing behavior, so applications without Sync can still remove unused WebSocket code. Applications whose dynamic handlers require the JIT fallback keep it automatically. Compiled applications with and without Sync are exercised end-to-end to cover both paths.

Bun uses Elysia's native Bun adapter, Vercel runs the Bun-targeted bundle through `app.handle(Request)`, and Cloudflare uses a dedicated Workers deployment path. Static exports have no server runtime, and package builds let the host application own its adapter. A Bun-targeted bundle cannot run in Workers merely by exporting a `fetch` handler.

## Bun Server Bundle

```sh
furin build --target bun
bun .furin/build/bun/server.js
```

The target directory contains `server.js`, one client directory per Furin instance, and copied `public/` assets. `.furin/build/manifest.json` records the exact paths and build IDs.

Deploy the whole `.furin/build/bun` directory. `server.js` resolves client assets beside itself; `FURIN_CLIENT_DIR` can override the root instance's directory when a platform mounts assets elsewhere.

## Docker Server Bundle

Use one immutable image containing the non-compiled server and its matching client/public assets. This example assumes a standalone application with a committed `bun.lock` and no runtime files outside Furin's output:

```dockerfile
FROM oven/bun:1.4.2 AS build
WORKDIR /app
COPY package.json bun.lock ./
RUN bun install --frozen-lockfile
COPY . .
RUN bunx --no-install furin build --target bun

FROM oven/bun:1.4.2 AS runtime
WORKDIR /app
ENV NODE_ENV=production
ENV PORT=3000
COPY --from=build --chown=bun:bun /app/.furin/build/bun/ ./
USER bun
EXPOSE 3000
CMD ["bun", "server.js"]
```

Create a `.dockerignore` beside it:

```text
node_modules
.git
.furin
.vercel
.env
.env.*
*.sqlite
*.sqlite-*
```

Supply secrets at runtime through the host's secret store, not Docker build arguments. Public `FURIN_PUBLIC_*` values are build-time inputs and must not contain secrets. Pin the image digest in your production CI if reproducible base images are required.

If the browser reads public configuration, declare **each actual variable** in the build stage before the Furin build. For example, replace the build command above with:

```dockerfile
ARG FURIN_PUBLIC_API_URL
RUN bunx --no-install furin build --target bun
```

Railway and Render supply configured service variables as Docker build arguments, but the Dockerfile must declare the matching `ARG` names to consume them. On Fly or local Docker, pass public values explicitly with `--build-arg FURIN_PUBLIC_API_URL=https://api.example.com`. Fly runtime secrets do not configure the browser build. Rebuild the image when a public value changes; setting it only on the running container cannot change emitted JavaScript.

For a monorepo, use the repository root as the Docker build context, copy workspace manifests before installing, and build the library before the selected application when it is a workspace dependency. Change the final `COPY` to that application's `.furin/build/bun` directory. Do not blindly use the standalone Dockerfile for a `workspace:*` application. Native modules, externalized dependencies, database migrations, and application-owned runtime files must also be included when the application needs them; a bundled server does not embed a SQLite database.

## Railway

Railway can run the [Docker server bundle](#docker-server-bundle) directly. Use Docker instead of relying on framework auto-detection:

1. Commit the Dockerfile, `.dockerignore`, and lockfile, then create a Railway service from the repository.
2. Set the Dockerfile/build context for the application. In a monorepo, preserve access to its workspace dependencies.
3. Set the healthcheck path to `/_furin/health/ready`.
4. Generate a public domain or attach a custom domain. Railway supplies `PORT`; let the generated Bun server read it.
5. Supply application secrets through Railway Variables. Configure the deployment drain/termination window to allow Furin's full graceful shutdown, at least 35 seconds plus an operational margin.

Configure these settings in the dashboard for a new service: Dockerfile builder/path, readiness healthcheck with a startup timeout appropriate to your app, and an on-failure restart policy. Railway's legacy `railway.toml`/`railway.json` Config as Code is deprecated and supported only for legacy services until **2026-12-01**; do not use it as a new deployment recipe. Use Railway's current [Infrastructure as Code workflow](https://docs.railway.com/infrastructure-as-code) when settings must be managed in source control.

### Railway CDN

Railway has a [native CDN](https://docs.railway.com/networking/cdn), currently in beta. Enable it in the service's **Settings > Edge**. Recommended initial configuration:

- **HTML Caching: Never**.
- Preserve origin cache headers for browser assets; do not force a TTL over `private` or `no-store`.
- Add an [Edge Rule](https://docs.railway.com/networking/edge-rules) with **Override cache > Bypass** for every path other than `/_client/*`, `/public/*`, and `/favicon.ico`. Include the corresponding prefixed paths for mounted Furin apps.

The bypass rule matters: disabling HTML caching alone does **not** disable JSON caching. Public `/_furin/data` responses can have cacheable headers, and an origin `revalidatePath()` does not purge Railway's CDN. If your plan does not provide the required Edge Rules, leave the native CDN disabled and use the [asset-only Cloudflare policy](#cdn-policy-for-bun-hosts) instead.

Request the same browser asset twice and inspect `x-cache: HIT` and `Age`. Check that page documents, navigation data, APIs, and healthchecks bypass the CDN. Railway compresses eligible responses with Brotli/gzip and passes through WebSockets and uncached streams.

Railway supports whole-service CDN purges, not per-URL purges. `railway cdn purge html` does not remove cached JSON navigation data; that requires `railway cdn purge all`. Purge-on-deploy is not mutation-time invalidation. Do not enable HTML/data edge caching until both variants and query strings have an explicit invalidation policy. Keep immutable assets available across releases rather than relying on them having reached every edge location.

See [Railway's Bun guide](https://docs.railway.com/guides/bun) and [Infrastructure as Code](https://docs.railway.com/infrastructure-as-code) for platform setup.

## Fly.io

Use the same Dockerfile and let Fly terminate TLS. A minimal `fly.toml` is:

```toml
app = "your-furin-app"
primary_region = "cdg"
kill_signal = "SIGTERM"
kill_timeout = "45s"

[build]
dockerfile = "Dockerfile"

[env]
PORT = "3000"
NODE_ENV = "production"

[http_service]
internal_port = 3000
force_https = true
auto_stop_machines = "off"
auto_start_machines = true
min_machines_running = 1

[[http_service.checks]]
grace_period = "10s"
interval = "15s"
timeout = "5s"
method = "GET"
path = "/_furin/health/ready"
```

Replace the app name and choose a region close to your database. Configure secrets with `fly secrets set`, then deploy with `fly deploy`. Fly Proxy is not a page-cache adapter: add the [asset-only CDN policy](#cdn-policy-for-bun-hosts) on your custom domain when edge asset caching is wanted.

Keep a single machine for a file-backed SQLite application, with an explicitly mounted volume and application-configured database path. For multiple machines, use shared PostgreSQL/Redis as appropriate; do not copy the local example database into each replica.

See [Fly's Dockerfile deployment guide](https://fly.io/docs/languages-and-frameworks/dockerfile/) and [configuration reference](https://fly.io/docs/reference/configuration/).

## Render

Create a Docker Web Service using the same Dockerfile, or commit a `render.yaml` Blueprint:

```yaml
services:
  - type: web
    name: furin-app
    runtime: docker
    dockerfilePath: ./Dockerfile
    dockerContext: .
    healthCheckPath: /_furin/health/ready
    maxShutdownDelaySeconds: 45
    envVars:
      - key: NODE_ENV
        value: production
```

Render supplies `PORT`; the generated server reads it. Add secrets in the dashboard, not the Blueprint. For a service created in the dashboard, set **Max Shutdown Delay** to 45 seconds too: Render's 30-second default is shorter than Furin's full drain window. Select a service plan with the uptime your application requires. Configure the [asset-only CDN policy](#cdn-policy-for-bun-hosts) on a custom domain: a Docker Web Service is not a static-site deployment and does not automatically provide Furin ISR invalidation at the edge.

See [Render Docker deployments](https://render.com/docs/docker) and the [Blueprint specification](https://render.com/docs/blueprint-spec).

## Self-Hosting And Coolify

Use the Docker image on a VPS, Docker Compose, or Coolify's Dockerfile deployment. In Coolify, set the application port to `3000`, configure the readiness healthcheck, supply secrets through its environment settings, and attach the production domain. The same cache and multi-replica rules apply; Coolify is an orchestrator, not a new Furin runtime.

For a single-host deployment:

```sh
docker build -t furin-app .
docker run -d --name furin-app \
  --env-file .env.production \
  -p 127.0.0.1:3000:3000 \
  --stop-timeout 45 \
  --restart unless-stopped \
  furin-app
```

The local environment file must stay outside version control and out of the image. Bind Bun to loopback at the host boundary and expose only the reverse proxy publicly. A Caddy starting point is:

```caddyfile
app.example.com {
  encode zstd gzip
  reverse_proxy 127.0.0.1:3000 {
    flush_interval -1
  }
}
```

Caddy terminates TLS and supports WebSocket upgrades; the negative flush interval avoids buffering streaming responses. When Caddy runs in Compose rather than on the host, proxy to the application service name, such as `app:3000`, on a private Docker network instead of `127.0.0.1`. Test streaming and idle timeouts with your workload; see the [production checklist](#production-checklist).

### CDN Policy For Bun Hosts

The recommended default is **same-origin CDN assets, origin-owned HTML/data caching**. It avoids an additional DNS/TLS connection for a separate asset domain and keeps `revalidatePath()` and `revalidateTag()` effective without an external page purge.

For Cloudflare in front of Railway, Fly, Render, or your VPS:

1. Attach your application domain to the origin and enable Cloudflare proxying for its DNS record.
2. Use **Full (strict)** TLS with a valid origin certificate, not Flexible TLS.
3. Create an asset Cache Rule matching only `/_client/*`, `/public/*`, and `/favicon.ico` (including mount prefixes). Make those paths eligible for caching and respect the origin's cache headers. Do not override private/no-store responses or cache missing assets and errors.
4. Create a later, overriding bypass rule for every non-asset path. Page documents, `/_furin/data`, APIs, events, Sync, and healthchecks must continue to reach the origin. Avoid a global “Cache Everything” rule.
5. Keep the full query string in cache keys. Let Cloudflare negotiate compression without buffering private streams.

`/_client` browser bundles use content-hashed filenames and can have a one-year immutable lifetime. Unversioned `public/` files and `favicon.ico` need a shorter TTL or explicit purging when changed; do not mark them immutable. Check their actual origin headers rather than assuming a platform's fallback TTL is appropriate. Only expose public assets, never `.furin/build/private`, server bundles, templates, or environment files.

Cloudflare should return `CF-Cache-Status: HIT` for a warmed asset. A miss can occur at another edge location; a local cache hit does not prove global distribution. For a public page and its navigation data, verify neither is served from the edge cache under this policy.

If you later cache public HTML/navigation data at the CDN, configure both the shared origin cache and a CDN purge integration. Purge all query-specific variants of both representations on mutation. Furin's `setCachePurger()` callback is best-effort, not a synchronous global freshness guarantee; monitor failures and accept a bounded TTL or keep those responses bypassed. Cloudflare Workers `cache.delete()` only purges the local datacenter and is not a global purge.

## Compiled Executables

```sh
# Executable plus client/public directories
furin build --target bun --compile server

# Framework and public assets embedded in the executable
furin build --target bun --compile embed
```

Both commands write `.furin/build/bun/server` on macOS/Linux and `.furin/build/bun/server.exe` on Windows. In `server` mode, deploy the executable together with its asset directories. In `embed` mode, Furin removes the external client directories after embedding them.

Use `embed` for the simplest single-artifact rollout. Use disk mode when a CDN, container layer, or packaged child application should serve or replace assets independently.

## Cloudflare Workers

The Cloudflare target is a **Workers runtime adapter**, not a compiled Bun server behind Cloudflare. Bun builds the application; Cloudflare runs the emitted Worker and serves browser/public assets through [Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/).

Use a default-exported Elysia application and guard `.listen()` with `import.meta.main`, as in the [server-entry example](#server-entry) below. The build selects Elysia's Workers-compatible adapter; the application does not need to import another adapter to build this target.

### Build And Deploy

```sh
furin build --target cloudflare
bunx --bun wrangler deploy --dry-run --config .furin/build/cloudflare/wrangler.jsonc
bunx --bun wrangler deploy --config .furin/build/cloudflare/wrangler.jsonc
```

Authenticate Wrangler separately before deploying. Deployment writes to your Cloudflare account; a Furin build does not publish anything.

Keep `bun run dev` for normal application development. Wrangler 4.100.0's local `dev` proxy currently hangs under Bun even for a minimal non-Furin Worker; it is not a verified Bun-local preview workflow. Furin's integration tests execute the emitted Worker in Miniflare/workerd and verify native HTTP requests, while Wrangler's Bun-driven `deploy --dry-run` validates the deployment artifact without publishing it. Pin your Wrangler version in the application's dev dependencies for CI, and verify platform-specific bindings separately.

The generated artifact has this shape:

```text
.furin/build/cloudflare/
├── wrangler.jsonc
├── worker.js
└── assets/
    ├── _client/
    ├── public/
    └── favicon.ico
```

Optional directories/files are present only when the application supplies them. Cloudflare uses one content-hashed `/_client/` namespace for browser assets across mounted applications, so server-rendered asset imports and browser imports resolve to the same files. Pages and framework data endpoints retain their configured mount prefixes. The Worker contains the compiled route tree and templates; private templates, loader snapshots, source maps, and server bundles are not public static assets.

Wrangler configuration uses `nodejs_compat` for supported Node APIs. This is not Bun compatibility: application dependencies using `Bun.file`, `bun:sqlite`, TCP listeners, or a local filesystem at request time still need a Workers-compatible replacement. Elysia's `file()` also cannot serve an origin filesystem in Workers; put those files in `public/`. Do not construct `Response` objects at module scope or use a prebuilt `Response` as an inline route value: construct it inside the request handler instead. These application-level runtime restrictions are not all detectable by the build, so a successful bundle alone is not proof that arbitrary application dependencies can run in Workers.

Only assets emitted by the browser build are automatically published. A file emitted only by the server bundle is rejected rather than referenced through a broken CDN URL or exposed accidentally. For a public image URL returned by a server loader, put the image in `public/` and return its public URL.

The adapter preserves `public/_headers` for native static asset responses and adds one immutable rule for the reserved `/_client/*` namespace, regardless of the number of chunks. Up to 99 custom rules remain available under Cloudflare's 100-rule limit. Do not supply `public/_client` files, mount an application inside `/_client`, or redefine the reserved rule. Custom security headers still apply to browser assets, while the adapter owns their immutable cache policy. `_headers` does not apply to Worker-rendered HTML/APIs; set their security headers in Elysia request handling.

### Supported Behavior

| Feature | Initial Workers target |
|---|---|
| SSR and browser hydration/navigation | Worker request handler |
| SSG | Built-in public route snapshot served by the Worker |
| Browser/public assets | Native Workers Static Assets CDN |
| ISR | Rejected: no globally coherent page-cache adapter yet |
| PPR / request loaders in cacheable documents | Rejected |
| SSR with inherited layout request loaders | Supported; SSR pages use `loader()` / `defer()` for their own request data |
| RSC | Rejected |
| Sync | Rejected |
| Application `@elysia/static` mounts | Rejected; use `public/` |
| Custom `pageCache`, Bun executable compilation, private server source maps | Rejected |

Do not gate unsupported `sync` or `pageCache` options on runtime environment variables. Constant options are rejected during the build, but a runtime-only value cannot always be detected there. The Worker validates them again at initialization and will fail to start if a deployment enables them. Keep these options absent for this target.

Asset requests are served by the platform without invoking the Worker when they match a deployed file. Non-asset requests go to the Worker; the assets configuration is not an SPA fallback that turns unknown routes into `200 index.html` responses.

The initial target does not cache page documents or navigation data at Cloudflare's edge. Treat dynamic Worker responses as origin responses, preserve their cache headers, and do not add a rule forcing personalized responses into a shared cache. Hashed browser files get immutable caching. Unversioned public files revalidate by default; custom `public/_headers` rules can change their policy, so use immutable caching only when those files are versioned.

Worker API responses and redirects without an explicit cache policy default to `private, no-store`. Explicit cache policies on non-HTML APIs remain application-owned; configure invalidation before opting them into an edge cache.

Workers' Cache API is datacenter-local, does not implement `stale-while-revalidate`, and `cache.delete()` is not a global purge. The adapter therefore rejects ISR rather than presenting isolate-local memory as a durable global cache. Use the Bun target with a shared page cache, or Vercel's native ISR, when those guarantees are required.

Bindings and secrets belong in Wrangler configuration and Cloudflare's secret store. Never put secrets in `FURIN_PUBLIC_*`. Keep the deploy configuration under version control outside generated output when adding bindings, custom domains, or platform-specific settings, and point its `main` and `assets.directory` at the generated files. Do not rely on edits inside `.furin/build` surviving the next build.

For example, a developer-owned root `wrangler.jsonc` can select the Worker name:

```json
{
  "$schema": "node_modules/wrangler/config-schema.json",
  "name": "your-furin-app",
  "main": ".furin/build/cloudflare/worker.js",
  "compatibility_date": "2026-06-01",
  "compatibility_flags": ["nodejs_compat"],
  "assets": {
    "directory": ".furin/build/cloudflare/assets",
    "html_handling": "none",
    "not_found_handling": "none"
  }
}
```

Build first, then use `bunx --bun wrangler deploy --config wrangler.jsonc`. Configure secrets using the same Worker name/configuration so they are attached to the intended deployment, not the generated default name.

### Static-Only Cloudflare Hosting

For an application containing only SSG pages, the existing static export is smaller and does not need a Worker:

```sh
furin build --target static
bunx --bun wrangler pages deploy dist
```

Use the configured static output directory if it is not `dist`. Static hosting has no SSR, APIs, request loaders, or runtime invalidation. Use a Pages project name appropriate to your account and do not confuse this static workflow with Workers SSR.

## Vercel

The Vercel adapter emits the [Build Output API v3](https://vercel.com/docs/build-output-api) directly. It uses the Vercel Bun runtime, serves browser and `public/` assets from the CDN, and keeps SSR, SSG, ISR, API routes, streaming, and SPA navigation in one Furin application.

Application `@elysia/static` mounts are not supported by this target and fail the build rather than deploying a missing runtime directory. Place files under `public/` to serve them through the CDN.

### Server entry

Export the Elysia application as the default export. Guard `.listen()` with `import.meta.main` so the same entry runs locally without opening a TCP listener inside a Vercel Function:

```ts
import { furin } from "@teyik0/furin";
import { Elysia } from "elysia";

const app = new Elysia().use(
  await furin({
    pagesDir: "./src/pages",
  })
);

export const port = Number(process.env.PORT ?? 3000);

if (import.meta.main) {
  app.listen(port);
  console.log(`Furin app running at http://localhost:${app.server?.port}`);
}

export default app;
```

The compiled Bun boot entry reads the exported numeric `port` when `PORT` is unset, so multiple workspace applications keep distinct local production defaults. Runtime `PORT` still takes precedence because the server module computes the export from the environment.

### Build

```json
{
  "scripts": {
    "build:vercel": "furin build --target vercel"
  }
}
```

The build writes a deployable artifact to `.vercel/output`:

```text
.vercel/output/
├── config.json
├── static/
│   ├── _client/
│   └── ...public assets
└── functions/
    ├── __server.func/
    │   ├── index.js
    │   └── .vc-config.json
    ├── index-ssg.func -> __server.func
    └── index-ssg.prerender-config.json
```

Add `vercel.json` when Vercel should run this target automatically:

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "buildCommand": "bun run build:vercel",
  "bunVersion": "1.4.x",
  "framework": null,
  "installCommand": "bun install --ignore-scripts"
}
```

You can also build and deploy the prebuilt artifact yourself:

```bash
bun run build:vercel
bunx vercel deploy --prebuilt
```

### Rendering and cache behavior

| Furin mode | Vercel output |
|------------|----------------|
| `ssr` | Bun catch-all Function |
| `ssg` | Prerender Function with `expiration: false` and a build-time HTML fallback when the URL is known |
| `isr` | Prerender Function whose expiration matches `revalidate`, with a build-time fallback for request-independent URLs |
| SSG/ISR with `requestLoader` (PPR) | Cached public HTML shell chained to a private streaming Function continuation |

Fixed ISR routes are rendered during the build, like Next.js. Dynamic SSG and ISR URLs returned by `staticParams()` receive individual build-time fallbacks. Routes with a declared `query` schema remain on-demand so the fallback cannot ignore query-dependent input. For PPR routes, only the public shell is prerendered: `requestLoader` does not execute during this phase. `revalidatePath()` and `revalidateTag()` invalidate the corresponding `Vercel-Cache-Tag`, while `waitUntil()` keeps background ISR regeneration alive after the response is sent.

The browser data endpoint `/_furin/data` stays behind the Bun Function, but successful SSG/ISR payloads without a `requestLoader` are cached by the CDN with the document's revalidation window. JSON-only results use a compact envelope; rich values, shared references, deferred data, and RSC keep the lossless CrossJSON/Route Frame transports. The document and all query-specific navigation payloads share one cache tag, so `revalidatePath()` and `revalidateTag()` purge them together.

Vercel owns the deployed SSG/ISR cache. Prerender Function invocations bypass Furin's process-local cache and return newly rendered HTML; the in-memory stale-while-revalidate implementation is used only in development and Bun deployments.

PPR stores the public HTML shell, React's opaque postponed state, and the public loader snapshot as one coherent artifact. The build generates known PPR shells using the **actual production bundle**, so minification cannot change the component tree between prerender and resume.

Vercel serves the public shell from its native cache and chains it to a Function that runs `requestLoader` and resumes the suspended boundaries. Both parts form one HTTP response; the browser does not fetch a separate continuation. Resume requests are authenticated with a build-scoped chain key and checked against the build and mounted route. The state is not included in the browser's HTML.

The personalized response and navigation payload remain `private, no-store`. Public artifacts also use Runtime Cache for origin rendering and navigation, scoped by deployment, build, mount prefix, route mode, and query string. Path and tag invalidation expires those entries. On Bun deployments, the same artifact is kept in memory; stale ISR artifacts remain usable while a tracked regeneration produces their replacement.

Consume request-loader field promises inside a React `Suspense` boundary. Furin uses React's Web Streams renderer for applications containing PPR routes so full renders and resumptions share the same React contexts. Applications without PPR keep the native Bun renderer and omit the resumable renderer from their server bundle.

The isolated Flight codec is included alongside the Function handler, so RSC rendering does not compile code or read framework sources at runtime.

SSR payloads, request-specific loaders, deferred streams, redirects, not-found results, and errors are explicitly `private, no-store`.

### Function region

Functions use Vercel's project default region (typically `iad1`). Place compute close to the application's data source through `furin.config.ts`:

```ts
import { defineConfig } from "@teyik0/furin/config";

export default defineConfig({
  vercel: {
    regions: ["cdg1"],
  },
});
```

The editor suggests [Vercel's supported compute regions](https://vercel.com/docs/regions#region-list), such as `cdg1`, `fra1`, or `iad1`. An empty list, duplicates, and unsupported identifiers fail config validation.

### Cold-start diagnostics

The generated Function uses a lightweight bootstrap in front of the application bundle. Dynamic responses expose:

```text
Server-Timing: furin_module_init;dur=104.74, furin_server_init;dur=12.8, furin_handler_wait;dur=0.1, furin_handler;dur=2.4
```

| Metric | Meaning |
|--------|---------|
| `furin_module_init` | Parse and evaluate the complete server bundle |
| `furin_server_init` | Import the user server entry and assemble the Elysia application |
| `furin_handler_wait` | Time the request waited for module initialization |
| `furin_handler` | Time Furin spent creating the response after initialization |

The first request handled by a Function instance also emits a structured `vercel_cold_start` event containing these timings, route/app counts, region, and raw server-bundle bytes.

Use `--analyze` to inspect which modules contribute to the bundles:

```bash
bunx furin build --target vercel --analyze
```

This writes one client metafile per mounted app (for example, `vercel-client.json` for the root app and `vercel-client-admin.json` for `/admin`) plus the shared `vercel-server.json` under `.furin/build/analysis`.

The executable reference is [`examples/weather`](https://github.com/teyik0/furin/tree/main/examples/weather).

```ts
// furin.config.ts
import { defineConfig } from "@teyik0/furin/config";

export default defineConfig({
  static: {
    basePath: "/my-site",
```

```sh
furin build --target static
furin preview
```

The output contains:

```text
dist/
├── index.html
├── __furin_data.ndjson
├── docs/
│   └── index.html
├── _client/
├── public assets...
```

Each rendered path also receives a route-data file so SPA navigation works without a runtime `/_furin/data` endpoint. Redirect loaders become portable HTML redirect pages.

Static export supports only SSG routes and rejects `requestLoader()`. Dynamic SSG routes require `staticParams()`. Keep `onSSR: "error"` unless another deployment deliberately owns the skipped SSR/ISR URLs.

Set `basePath` only when the host serves the site below a subpath. It updates asset URLs and client navigation; it is not the same setting as the runtime `furin({ prefix })` used by a Bun server.

## Environment Variables

Server secrets stay in `process.env` and are read only by server code. Do not expose secrets through the browser build.

Client-visible values must match the Bun full-stack allowlist used during development:

```toml
[serve.static]
env = "FURIN_PUBLIC_*"
```

Treat every `FURIN_PUBLIC_*` value as public, because it may be compiled into browser code.

## Caches And Replicas

SSG/ISR HTML caches are in-process unless `furin({ pageCache })` receives a shared adapter. A CDN can cache their public responses, but on-demand invalidation must evict both the origin entry and the CDN entry. For multiple Bun replicas, create `redisPageCache()` once per process and use one stable namespace across replicas and releases. Do not include a replica ID or build ID in that namespace. See [Shared Page Cache](/docs/caching#shared-page-cache) for the complete setup.

Vercel Build Output is the exception: omit `pageCache` and let the deployment adapter use Vercel's native prerender and Runtime Cache integration. A custom page cache is intended for self-hosted Bun replicas, and configuring one on the Vercel target fails fast instead of creating a second source of truth.

The Sync journal distributes browser invalidations but is not a shared HTML cache. A Redis Sync adapter and a Redis page-cache adapter may use the same server, but they are separate contracts and should use distinct namespaces.

For Sync, use file-backed SQLite only on one host. For replicas on separate hosts, PostgreSQL with its native `LISTEN/NOTIFY` notifier is the recommended default; Redis remains available as either the durable adapter or an independent notifier. Keep one stable namespace and run the required schema bootstrap before starting traffic. See [Sync & Invalidations](/docs/sync).

## Production Checklist

### Reverse proxy, compression, and streaming

Put a reverse proxy or load balancer in front of Bun. Let it terminate TLS and negotiate Brotli/gzip; Furin deliberately does not compress responses in the application process. Brotli normally saves more bytes than gzip for HTML, JS, and CSS, while gzip remains the compatibility fallback. Do not compress already-compressed images or add buffering to streaming SSR, PPR, SSE, and Sync WebSockets. Preserve `Content-Encoding`, `Vary: Accept-Encoding`, cache headers, `Upgrade`, and forwarded host/protocol headers. An Nginx-style starting point is:

```nginx
# In the http block:
map $http_upgrade $connection_upgrade { default upgrade; '' close; }
upstream furin { server 127.0.0.1:3000; keepalive 32; }

server {
  listen 443 ssl;
  # Configure certificates and HTTP/2 for your environment.
  gzip on;
  gzip_vary on;
  gzip_types text/css text/javascript application/javascript application/json image/svg+xml;
  # If the Brotli module is installed: brotli on; brotli_types text/html text/css text/javascript application/javascript application/json image/svg+xml;

  location / {
    proxy_pass http://furin;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
    proxy_buffering off;
    proxy_connect_timeout 5s;
    proxy_read_timeout 120s;
    proxy_send_timeout 120s;
  }
}
```

Verify your actual proxy build supports Brotli before enabling it. Test both `Accept-Encoding: br` and `Accept-Encoding: gzip`; with a gzip-only proxy, gzip is a valid production contract. Keep streaming responses unbuffered and set idle/read timeouts above the longest expected interval between chunks. Bun also has its own default 10-second `idleTimeout`: it counts silence while a loader is still running, so the 120-second proxy timeout above cannot prevent Bun from resetting a slow request. Export `idleTimeout` (seconds) from `src/server.ts` for the generated Bun boot, or pass it to `startProductionServer()` in a custom boot; choose it for your workload and test a response with a delayed first byte through the public endpoint. Restrict direct Bun access to trusted networks and never expose `.furin/build/private` as static content. See [Bun server timeouts](https://bun.sh/docs/runtime/http/server#idletimeout).

### Health and graceful shutdown

The generated Bun server exposes `/_furin/health/live` and `/_furin/health/ready`. Both return `Cache-Control: no-store`. Liveness means the process is running; readiness means it should receive application traffic. On `SIGTERM` or `SIGINT`, readiness becomes 503 immediately, while application requests continue to be served during the five-second load-balancer propagation window. Liveness remains 200 during the drain. After that window, Furin rejects new application requests, closes its browser-event WebSockets, stops accepting connections, waits for in-flight HTTP requests, ISR regeneration, deferred request-log emissions, and Sync cursor unsubscriptions, then calls an optional application `onShutdown` export. The 30-second deadline covers this entire drain; when it expires, Bun force-closes remaining sockets and Furin stops waiting for unfinished drains. Signal-triggered shutdown then exits the process with its existing exit code (or 0), or with 1 if cleanup throws. Calling `shutdown()` programmatically does not exit the process. Configure your orchestrator's termination grace period above 35 seconds with an operational margin. The proxy must remove a replica when readiness fails; use liveness only to detect a stuck process, not to decide traffic routing.

```ts
// src/server.ts — optional, for clients owned by the application
export async function onShutdown() {
  await redis.quit();
  await database.end();
}
```

Furin closes its own Sync subscriptions but does not close application-owned Redis or PostgreSQL clients; close those in `onShutdown` after the framework drain. An application exporting a custom `startServer()` owns its listener and signal handling instead of the generated boot path. It can use `startProductionServer()` from `@teyik0/furin/production-server` to adopt the same lifecycle, or implement equivalent probes and draining itself. A direct `bun src/server.ts` development start also uses the application's own `.listen()` path.

### Private server source maps and error tools

Server source maps are off by default. Enable them for Bun and Vercel builds:

```ts
import { defineConfig } from "@teyik0/furin/config";

export default defineConfig({ serverSourceMaps: true });
```

Furin uses Bun's `external` mode, which does not add a public `sourceMappingURL` comment, and moves the maps to `.furin/build/private/server-sourcemaps/{bun,vercel}`. These maps are **not** included in `.furin/build/bun` or `.vercel/output`; upload them from CI before starting the new release. Keep that private directory restricted because maps can contain source content. For Sentry, stage the generated server `.js` files and their matching `.map` files together outside the deployable directory, then run `bunx @sentry/cli sourcemaps upload --org <org> --project <project> --release <release> <staging-dir>` with `SENTRY_AUTH_TOKEN` supplied by CI. Upload the same release identifier used by the server SDK and verify a test error is symbolicated. For another error tool, upload the same JS/map pairs using its supported artifact API; no credentials are embedded by Furin. Compiled executables can also emit private maps, but check your error tool's support for Bun executable stack frames before relying on remote symbolication.

### Rolling deploys, state, and recovery

Deploy code and its matching client assets as one immutable release. Build and upload source maps, run compatible database migrations, and ensure shared Redis/PostgreSQL dependencies are reachable before adding the new replica to the load balancer. Wait for readiness, gradually shift traffic, then send `SIGTERM` to old replicas and leave the full drain window before `SIGKILL`. Roll back the code and matching assets together. Keep the page-cache namespace stable across replicas and releases; invalidate incompatible entries explicitly rather than encoding a replica ID in the namespace. CDN caches need their own purge/TTL policy for on-demand invalidation.

At the CDN, honor Furin's `Cache-Control` and include the full URL, including query string, and content encoding in the cache key. Do not cache personalized SSR, `requestLoader` results, errors, or Sync responses. Public SSG/ISR HTML and cacheable `/_furin/data` responses may follow their headers. On self-hosted Bun, `revalidatePath()` and `revalidateTag()` invalidate the origin cache, not an arbitrary external CDN; configure a separate CDN purge or bypass its HTML/data cache when immediate invalidation is required. Keep versioned client assets available while pages from the previous release can still reference them. Vercel's adapter handles its own CDN invalidation.

Keep secrets in the deployment secret store; never put them in `FURIN_PUBLIC_*`, client build flags, source maps, or logs. Back up the authoritative PostgreSQL/Redis data, including Sync journals and any durable page-cache state you require, with point-in-time or AOF/snapshot recovery appropriate to the service. Test restoration and schema compatibility before relying on backups. An in-memory cache is disposable and should not be treated as a backup.

For recovery, restore the application database and durable Sync journal to a consistent point, apply the required Sync schema migration, then start replicas against the restored store. Restore Redis page-cache state only when it is compatible with that application snapshot; otherwise let public pages regenerate from authoritative data. Rehearse the procedure in an isolated environment by reading a known Sync cursor and rendering an ISR page before admitting traffic. File-backed SQLite Sync requires a consistent snapshot of its database file on the single host.

- Run type-checks and tests before the build.
- Deploy the exact server and asset directories listed by the manifest.
- Keep `NODE_ENV=production` behavior and server-only secrets consistent across replicas.
- Route load-balancer traffic using `/_furin/health/ready`; monitor `/_furin/health/live` separately.
- For multiple Bun replicas, verify Redis connectivity and keep the page-cache namespace stable across releases.
- Decide whether CDN invalidation is required before enabling long shared-cache lifetimes.
- Roll back code and matching assets together; the build ID protects browsers from mixed deployments, not the origin from an incomplete rollout.
